# UI_UX.md — UI-паттерны платформы

## [RULE] Продуктовые принципы

- Проектировать для работающего администратора, не для структуры базы данных.
- Одно понятие — один видимый элемент управления. Дублирующие блоки комментария/суммы/статуса/источника удаляются.
- Наиболее часто редактируемая информация — ближе к верху рабочей карточки.
- Связанные элементы управления читаются как одна группа; внутренние и клиентские данные визуально разделены.
- Сохраняется текущая тёмная дизайн-система, отступы, радиусы, общие компоненты.

## [RULE] Таблицы и адаптивность

- Горизонтальная прокрутка избегается там, где её решает адаптивная иерархия или плотностный tier.
- Существенные даты/статусы не обрезаются до неоднозначности.
- Длинный текст переносится естественно; управляемая вертикальная прокрутка допустима, горизонтальная — нет.
- Переиспользуются общие pill/metric-card/toggle/dialog/status-компоненты.

## [RULE] Состояния

Каждый элемент управления данными различает, где применимо: загрузка; сохранено; несохранено/автосохраняется; ошибка валидации; пусто/не указано; явный ноль/false; подтверждённое исключение; устарело/просрочено; отменено/архивировано. Цвет — не единственный носитель смысла.

## [RULE] Автосохранение

Крупные формы используют `useAutosave` (`use-autosave.ts`). Новые поля обязательно включаются в сериализацию, сравнение, восстановление, отклонение черновика и обновление базовой точки после сохранения. Восстановление черновика не должно запускать пересчёт бизнес-логики или дублировать импортированный текст.

**[RULE] (из `AGENTS.md`, «Редактируемость связанных сущностей»)**: если редактор связанной сущности открывается поверх большой формы с автосохранением — перед открытием обязателен `flush()` черновика родительской формы (`onBeforeEditRelated` в `WorkDocumentsSection.tsx`), чтобы не потерять несохранённые данные основной карточки.

## [RULE] Булевы бизнес-исключения — не голый checkbox

Перенесено из `AGENTS.md`. Булевы поля, представляющие **осознанное бизнес-исключение** (не «настройка интерфейса» и не «фильтр списка»), реализуются через `ConfirmableStatusToggle` (`src/components/ui/confirmable-status-toggle.tsx`), не голым `<input type="checkbox">`.

**Три категории — определить, к какой относится новое булево поле, ПЕРЕД тем как писать код:**

| Категория | Компонент | Пример |
|---|---|---|
| Обычный фильтр списка | `ToggleChip` (`toggle-chip.tsx`), без подтверждения | сортировка/фильтр в таблице |
| Безопасная настройка интерфейса (не влияет на бизнес-логику/отчётность) | обычный переключатель/чекбокс | визуальные предпочтения |
| Значимое бизнес-исключение | **только** `ConfirmableStatusToggle` | «Ссылка на Яндекс.Диск не требуется» (`ScheduleEvent.yandexLinkRequired`/`nasLinkRequired`) |

**[RULE]** Для категории «значимое бизнес-исключение»:
1. Подтверждение диалогом при включении, аудит через `writeAuditLog`, рядом с флагом — `confirmedAt`/`confirmedById`/`reason` метаданные на той же записи, не в отдельной таблице (образец — `yandexNotRequiredConfirmedAt/By/Reason` на `ScheduleEvent`).
2. Подтверждённое исключение визуально отделяется от «поле забыли заполнить» (предупреждающий контур, disabled-поле, поясняющий текст «Подтверждено: …»), не пустое поле как обычно.
3. Все разделы, показывающие поле (дашборд, заказ, карточка клиента, таблица «Заказы», отчёты), читают одно и то же состояние — не заводят по-разному интерпретирующие копии.
4. Любая проверка «заполнено/не хватает» различает ТРИ исхода: заполнено / пусто-и-обязательно / пусто-но-подтверждённо-не-требуется — последние два не сводятся в один (см. `docs/business/ORDERS.md`, раздел «Материалы», и `docs/business/MONTAGE.md`, раздел «Материалы» — оба используют этот же трёхсторонний паттерн).
5. Возврат из исключения в обычный режим (`false → true`) НЕ требует подтверждения — это возврат к более строгой проверке, не новое исключение.

**[CURRENT] Прецедент**: `RequiredLinkToggle` → `ConfirmableStatusToggle` (2026-07), первое применение этого паттерна.

## [RULE] Дисциплина крупных компонентов

При редактировании большой модалки — предпочитать выделение цельной секции с типизированными props, а не добавление ещё одной независимой машины состояний. Не выполнять несвязанный визуальный редизайн во время задачи по бизнес-логике.
