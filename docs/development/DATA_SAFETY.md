# DATA_SAFETY.md — безопасность данных и целостность аудита

## [CURRENT] Реальность окружения

Один владелец, одна база (Yandex Cloud Managed PostgreSQL) для dev И prod одновременно, деплой через Vercel, без CI/Docker/staging. **[RULE]** Правила ниже жёстко привязаны именно к этому масштабу — не разрастаться до enterprise-архитектуры (hash-цепочек, outbox pattern, множества окружений), которая этому масштабу не соответствует.

**[CURRENT]** Комментарии о провайдере БД раньше противоречили друг другу (часть указывала Timeweb, актуальная — Yandex Cloud). Исправлено в `prisma/schema.prisma:2` и `.env.example` коммитом `238ec35`. **[RULE]** Не выводить поведение, специфичное для провайдера, из комментариев — проверять `DATABASE_URL` без раскрытия значения, при сомнении спрашивать владельца.

## [CURRENT] Прецедент 2026-07-15 — стирание журнала аудита

Одноразовый ad-hoc Node/Prisma-скрипт (написан и запущен для уборки одной тестовой строки) обратился к несуществующему полю (`order.scheduleEventId` вместо `order.scheduleEvent.id`), получил `undefined`, и `prisma.auditLog.deleteMany({ where: { entityId: undefined } })` превратился в удаление БЕЗ условия — стёрло все 1799 строк журнала аудита (`cms_audit_log`) в единственной продовой базе.

## [RULE] Правила (прямая реакция на инцидент выше, не общая теория)

1. **`cms_audit_log` физически append-only на уровне БД**, не только по соглашению в коде: `BEFORE UPDATE/DELETE/TRUNCATE` триггер (`prisma/manual-sql/audit-log-append-only.sql`) отклоняет исключением любую попытку изменить/удалить существующую строку — для ЛЮБОЙ роли, включая ту, которой работает всё приложение. Не управляется Prisma (`db push`/`migrate` не знает о триггерах) — применяется вручную через `psql -f`. Методы вроде `deleteAuditLog`/`clearAuditLog`/`purgeAuditLog` не добавляются в код — их не должно быть, БД всё равно откажет.
2. **Перед ЛЮБЫМ `deleteMany`/`updateMany`/`delete` в ad-hoc скрипте против продовой базы** — сначала `findFirst`/`findUnique`, чтобы увидеть реальную строку и её `id`, удалять/менять по этому найденному литералу, не по повторно вычисленной переменной. Prisma молча трактует `undefined` в `where` как «условие отсутствует» — это и есть механизм, который стёр таблицу целиком. Если значение в `where` пришло через переменную/поле объекта — залогировать его перед выполнением и убедиться, что оно не `undefined`.
3. **Критичная бизнес-история не должна зависеть только от общего `AuditLog`.** Если сущности нужна предъявляемая пользователю история изменений (пример: `SubscriptionAdjustment`, см. `docs/business/SUBSCRIPTIONS.md`) — заводится отдельная иммутабельная таблица, запись в неё идёт в ОДНОЙ транзакции вместе с изменением данных и записью в `AuditLog` (`updateSubscriptionHours`/`chargeEventToSubscription`, `src/lib/actions/subscriptions.ts`) — не должно быть ситуации «данные изменились, история — нет» из-за падения между двумя отдельными вызовами.
4. **Если специализированная история не восстановима за период до какой-то даты** (как случилось здесь) — UI обязан честно показать это отдельной пометкой («История до … частично недоступна из-за ранее произошедшей потери журнала»), не молчаливым «корректировок не было» (образец — `getSubscriptionAdjustmentHistory` + `SubscriptionDetailModal.tsx`). Реконструированные/неполные данные не выдаются за полную историю.
5. **Ежедневный backup БД** через GitHub Actions (`.github/workflows/db-backup.yml`, cron 00:00 UTC = 03:00 МСК), не зависит от того, включён ли ноутбук. Секрет `DATABASE_URL` уже в репозитории. Артефакт хранится 90 дней (лимит GitHub) — не полноценный долгосрочный архив (12+ месяцев), известное ограничение. **[RULE] «Настроен» ≠ «работает»** — 2026-07-22 обнаружилось, что все запланированные бэкапы молча падали минимум 6 дней подряд (`pg_dump: error: aborting because of server version mismatch` — apt даёт postgresql-client 16, управляемый Postgres в Yandex Cloud уже 17.x). Перед операцией, для которой нужен свежий backup — проверить `gh run list --workflow=db-backup.yml`, не полагаться на факт существования job.
6. **Перед любой деструктивной операцией** (миграция, меняющая/удаляющая колонку, массовое изменение данных, восстановление backup) — сначала `npm run db:backup` вручную (или `gh workflow run db-backup.yml`, если `pg_dump` не установлен локально), если с последнего автоматического бэкапа прошло значимое время, и проверка, что `DATABASE_URL` действительно указывает на ожидаемую базу (`psql "$DATABASE_URL" -c "SELECT current_database();"`). Перед миграцией, меняющей ТИП существующей колонки (пример: `Document.number` Int→String, 2026-07-22) — сначала прочитать реальные данные в затронутых колонках, оценить риск заранее, не полагаться только на то, что Prisma не попросит `--accept-data-loss`.
7. **Никогда не выполнять `prisma migrate reset`, `DROP DATABASE`, `TRUNCATE` на продовой базе** — единственная база одновременно и dev, и prod (осознанное решение владельца, не ошибка). Команда, которая в обычном проекте была бы «сбросить dev-базу», здесь равна «стереть все рабочие данные платформы».
8. **DB-роль приложения (`studio_lk_user`) — владелец всех таблиц** (нет отдельной роли с урезанными правами для рантайма) — осознанно отложено, не единственная защита. Полагаться на append-only триггер (п.1) и дисциплину при ad-hoc скриптах (п.2), не на права роли.
9. **Любая потеря/подозрение на потерю данных** — сначала честный отчёт (что удалено, когда, почему, что пострадало в интерфейсе, что доступно для восстановления), потом код. Не говорить «всё работает», если исторические данные утрачены — явно перечислить, что именно и как это видно пользователю.

## [CURRENT] Схема без версионированных миграций

Нет каталога `prisma/migrations` — `db push` основной механизм. Пока это не изменено владельцем:
- предпочитать аддитивные nullable-поля;
- никогда не удалять/переименовывать без поэтапного плана совместимости;
- смотреть сгенерированный SQL, где возможно;
- запускать `prisma db push` только с явным подтверждением;
- **[RULE]** перезапускать Node/dev-процесс после `db push`, иначе Prisma Client работает по устаревшей схеме (частая причина расплывчатых runtime-ошибок сразу после миграции).

## [RULE] Паттерн скриптов миграции данных

Установленный паттерн для любого ad-hoc/разового скрипта, трогающего продовые данные:
- чистый `core.ts` + тесты;
- `dry-run.ts`, выводящий счётчики и примеры затронутых строк;
- `apply.ts`, идемпотентный по стабильному ключу/fingerprint (повторный запуск не должен создавать дубликаты или откатывать уже применённые изменения);
- вывод резервной копии там, где уместно;
- откат (`rollback`) — только опционально и только если он действительно безопасен.

**[RULE]** Не запускать `apply.ts` только потому, что задача звучит как «поправить старые данные» — сначала показать результат dry-run и получить подтверждение владельца.

## [RULE] Не доверять `supabase/`

Каталог `supabase/` в репозитории не считается текущей архитектурой без явного подтверждения владельца (см. `docs/architecture/PLATFORM_OVERVIEW.md`, риск №8). Текущий доступ к данным приложения — Prisma + PostgreSQL напрямую.
