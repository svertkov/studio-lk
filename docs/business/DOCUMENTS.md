# DOCUMENTS.md — реестр документов (договоры/приложения/счета/акты)

## [CURRENT] Область действия

Платформа ведёт структурированный реестр номеров и статусов документов (`Document`, `src/lib/document-model.ts` + `src/lib/actions/documents.ts`) — **[RULE] не файловое хранилище**. PDF/файлы не хранятся и не должны храниться без отдельного нового решения владельца; наличие записи `Document` не означает существование файла.

**[TARGET]** Модель осознанно спроектирована так, чтобы в будущем можно было добавить хранение файла/ЭДО/автогенерацию без изменения текущих полей — новые возможности добавляются через новые nullable-поля поверх, не переиспользуя существующие поля не по назначению.

**[CURRENT]** Timeline документооборота (создан → приложение → счёт → оплата → акт → закрыт) не реализован — это задел на будущее, не выдавать за существующий функционал.

## [RULE] Источники истины

1. Номер комплекта работы (`Счёт №127-1`, `Акт №127`) по умолчанию живёт на самой работе — `Order.documentPackageNumber` / `MontageProject.documentPackageNumber`, не копируется в каждый `Document`. Отображаемый номер — чистая функция `getDocumentDisplayNumber`, обычно не хранимое поле, **если только администратор не задал ручной номер** (см. «Ручная нумерация» ниже), который побеждает.
2. Статус оплаты счёта НЕ хранится на `Document` — читается из существующего источника (`Order.paymentStatus` через `payment-model.ts` для заказов, `MontageProject.clientPaymentStatus` для монтажа) через `getDocumentPaymentState`. Второй параллельный `paymentStatus` на документе не заводится.
3. Итоги счёта/акта со строками (`InvoiceLineItem`) — производные от этих строк. Второе редактируемое поле-дублёр итога не заводится нигде в UI (см. `recomputeDocumentAmount`, `actions/documents.ts`) — форма создания счёта в `WorkDocumentsSection.tsx` намеренно не принимает ручную сумму для INVOICE, только для APPENDIX (у которого строк нет). Тот же принцип действует для любого будущего document-типа со своими строками.
4. Требования режима документооборота («какие типы флоу требуют счёт/акт») берутся только из типизированных констант/хелперов `document-model.ts` — не копируются по компонентам (см. прецедент ниже).
5. RBAC для документов пока не реализован (как почти везде в проекте, см. `docs/security/SECURITY.md`) — не предполагать, что он есть, при расширении этой области.

## [RULE] Прецедент — тройное дублирование требований флоу (2026-07-19)

Требования режима документооборота однажды уже утекли в три независимых места одновременно (`document-model.ts`, `getDocumentsDashboardStats`, `OrdersListView.tsx`) при добавлении `DocumentFlowType.CONTRACT_APPENDIX_INVOICE_ACT` — полный разбор инцидента и практический вывод (обязательный `grep -rn` по enum при добавлении нового значения) см. в `AGENTS.md`, раздел «Единый источник данных», не пересказывается здесь повторно во избежание второго источника истины по одному и тому же инциденту.

## [RULE] Нумерация

- Сквозные номера (договор, комплект работы) выдаются только через `DocumentCounter` (атомарный upsert+increment) — не генерируются иначе, не присваиваются вручную без прохождения через `bumpCounterIfLower`.
- `APPENDIX` (приложение к договору) — номер сквозной **в рамках одного договора** (`contractId`+`number`, `getNextAppendixNumber`), НЕ через `DocumentCounter`, в отличие от номера договора и номера комплекта работы. Клиент приложения не хранится напрямую (`clientId` остаётся `null`) — определяется через `contract.clientId`.
- Уважать частичные уникальные индексы в `prisma/manual-sql` (`cms_document_numbered_type_unique` — уникальность в рамках ТИПА документа, счёт №5 и акт №5 не конфликтуют друг с другом; не путать с уникальностью APPENDIX, которая декларативна в схеме через `contractId`+`number`).

### [CURRENT] Ручная нумерация (2026-07-23 и 2026-07-27)

- `Document.number` для INVOICE/ACT — необязательное ручное поле, как у APPENDIX, но с другой семантикой очистки: у APPENDIX номер обязателен (пустая строка — ошибка ввода), у INVOICE/ACT пустая строка — явный откат к вычисляемому `workPackageNumber`+`suffix` (не ошибка). Номер документа и `DocumentStatus` — независимые поля: ручной номер не подразумевает и не меняет статус.
- **[CURRENT] (2026-07-27, коммит `9f0105c`)**: поле ручного номера договора — свободный текст (`<input type="text">`, было `type="number"`), поддерживает символы вроде `/`, `.`, `,` и буквы (пример реального формата: `20-02.26`). Чекбокс «Указать исторический номер вручную» убран — поле показывается всегда. Рядом — подсказка-чип со следующим номером по `DocumentCounter` (`getNextContractNumberPreview`, тот же визуальный паттерн `GlowPill`, что у промо-скидки «−20% первый визит») — это только предпросмотр, счётчик не трогает; повторное открытие/закрытие диалога не пропускает номера.

## [RULE] Семантика копирования

«Создать на основании» — всегда снапшот, не живая синхронизация:
- `serviceDescription` (описание услуги) — ручной свободный текст у `APPENDIX`/`INVOICE`/`ACT`, независимый у каждого документа. Кнопки «Заполнить из…» в UI — одноразовое копирование в момент создания, изменение текста в одном документе не меняет текст в другом задним числом.
- **Акт «на основании счёта»** (`createActFromInvoice`, `Document.sourceInvoiceId`, self-relation `"ActFromInvoice"`, отдельная от `contractId`/`"ContractLink"`) — одноразовый snapshot: номер и строки (`InvoiceLineItem`) копируются один раз как НОВЫЕ записи в момент создания; дальнейшие правки счёта не отражаются на уже созданном акте задним числом. Тот же принцип распространяется на любое будущее «создать X на основании Y».
- **Копирование строк между документами — два разных пути**: `createActFromInvoice` создаёт НОВЫЙ акт из счёта (ставит `sourceInvoiceId`). `copyInvoiceLineItemsIntoAct` копирует строки в УЖЕ существующий акт (`REPLACE`/`APPEND`) и НЕ трогает `sourceInvoiceId`, если он уже задан — отдельное действие «обновить состав», не повторное указание источника. Оба используют общий `buildLineItemCreateManyData` для маппинга полей строки — не дублировать этот список в третий раз.

## [RULE] Создание и редактирование

- Услуги — обязательная часть счёта/акта с самого создания, не донастройка после. `createDocument` (`actions/documents.ts`) принимает необязательный `lineItems[]` и создаёт документ + все строки ОДНОЙ транзакцией; валидация всех строк (`validateLineItemDraft`, `document-model.ts`) происходит до открытия транзакции — ни один документ не остаётся «успешно созданным» пустым при ошибке в строке. Форма в `WorkDocumentsSection.tsx` держит черновик строк в обычном React state (`draftLineItems`) до финальной кнопки — паттерн «сначала пустой документ, потом отдельно добавить первую услугу» не повторяется.
- `DocumentLineItemsEditor` (переименован из `InvoiceLineItemsEditor`) рендерится и для ACT, и для INVOICE — компонент type-agnostic (`addInvoiceLineItem` и т.п. работают по `documentId`). Перед тем как заводить второй похожий редактор строк для нового document-типа — проверить, можно ли переиспользовать этот.
- **[RULE]** Требования к редактированию документных реквизитов (серверная проверка уникальности/прав, отдельная audit-запись `APPENDIX_NUMBER_CHANGED`, запрет копии номера на других экранах) — канонически описаны в `AGENTS.md`, раздел «Редактируемость связанных сущностей», правила 5/6/8; не пересказываются здесь повторно, чтобы не создавать второй источник истины.

## [CURRENT] Лейблы статусов

`DOCUMENT_STATUS_LABELS` — только текст, не источник истины по смыслу. Русские подписи менялись (2026-07-23: INVOICE/ACT статусы приведены к пользовательскому словарю) без изменения значений enum. **[RULE]** Не полагаться на конкретный текст лейбла при чтении/грепе кода — ориентироваться на имя enum-значения (`DRAFT`, `PREPARED` и т.п.).

## [RULE] Прочее

- Суммы приложений используются только для сверки/предупреждения (`appendixAmountMismatches`, `MontageFinanceBreakdown.tsx`) — источник финансовой истины остаётся `Order.preliminaryAmount`/`MontageProject.clientAmount`, ничего не пересчитывается автоматически.
- Историческая AI-миграция данных из Google-таблиц (2026-07-14) не переносит приложения — в исходных таблицах студии их нет вообще, только договоры/счета/акты.
- Новый документный функционал по-прежнему проверяется по общему чек-листу «Единого источника данных» (клиент, заказ, монтаж, CRM, финансы, дашборд, документы) — см. `AGENTS.md`.
