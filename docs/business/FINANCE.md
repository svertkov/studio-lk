# FINANCE.md — финансы

## [CURRENT] Обязательный словарь

### Выручка по заказу
Полная сумма, оплаченная/начисленная за съёмку/заказ. Для связанного бронирования эффективная сумма следует установленному merge-правилу заказ/расписание (`Order.preliminaryAmount` / `ScheduleEvent.estimatedPrice`, приоритет — см. `ORDERS.md`).

### Прибыль по заказу
«Прибыль по заказу» — полностью ручной результат, введённый администратором, хранится в `Order.netProfitManualAmount`.

**[RULE]** Платформа никогда не вычисляет, не предлагает и не заменяет автоматически это значение из выручки, налогов, расходов, монтажных выплат, способа оплаты, типа события или любой другой формулы.

Семантика:
- `null` = прибыль не введена;
- `0` = администратор явно подтвердил нулевую прибыль;
- отрицательные значения = убыток, должны оставаться валидными;
- изменение выручки, способа оплаты, монтажа или типа события НЕ должно менять прибыль.

**[CURRENT]** `Order.netProfitMode` и старые override-поля — исторические колонки обратной совместимости (см. `PLATFORM_OVERVIEW.md`, риск №6). **[RULE]** Новая бизнес-логика не возвращает поведение AUTO/MANUAL.

### Финансовый комментарий
`Order.financeComment` — внутреннее свободнотекстовое объяснение налогов, выплат, подрядчиков, транспорта, распределения между владельцами, причины нулевой/отрицательной прибыли. **[RULE]** Никогда не включается в Google Calendar, Telegram-сообщения, счета, акты, договоры или другой клиентский вывод.

## [CURRENT] Агрегаты дашборда

Канонический агрегат по заказам — `getOrdersFinanceSummary()` (`src/lib/actions/orders.ts`):
- «Выручка» = сумма эффективной выручки по включённым заказам;
- «Прибыль по заказам» = сумма ненулевых (не-`null`) ручных значений прибыли;
- отсутствующая прибыль остаётся различимой и считаемой отдельно от нулевой;
- нулевая прибыль вносит ноль, но не считается отсутствующей;
- отменённые/удалённые/черновые записи исключены по общим правилам запроса;
- выручка и прибыль используют одну и ту же выборку заказов и период.

**[RULE]** Не показывать вторую конкурирующую метрику под общей подписью «Прибыль».

## [RULE] Раздельные реестры

`Expense` — отдельный реестр. Общестудийные расходы НЕ вычитаются автоматически из «Прибыли по заказам» — администратор уже учитывает специфичные для заказа расходы при ручном вводе прибыли.

`MontageProject` имеет собственные суммы клиента/редактора и вычисляемый P&L монтажа (`montage-model.ts`, см. `MONTAGE.md`). Суммы монтажа не копируются в заказы или визиты. При объединённом отображении финансов области (scope) должны быть промаркированы точно, без двойного счёта.

`ClientVisit` — историческая импортированная финансовая/посещаемостная информация. Автоматически НЕ эквивалентна текущим финансам заказа. Любое изменение дашборда должно явно решать, чей это охват: заказы, исторические визиты, монтаж, расходы или объединённый вид.

## [CURRENT] Текущая осторожность

`computeCombinedFinanceSummary()` (`src/lib/finance-model.ts`) по-прежнему вычисляет историческую объединённую выручку/расходы/прибыль-подобные значения для вторичных разбивок; сейчас в объединение включены также выручка/расходы/прибыль монтажа (см. `MONTAGE.md`, раздел «Финансы»). **[RULE]** Не должна становиться второй первичной «прибылью» рядом с ручной прибылью заказа.

## [RULE] Требования UI

- Суммы в рублях с читаемой группировкой разрядов.
- Ноль сохраняется, не превращается в пустое поле.
- «Не указана» показывается только для `null`.
- Отрицательная прибыль разрешена и отображается.
- Цвет не единственный носитель смысла.
- Выручка, прибыль и комментарий визуально сгруппированы, но семантически разделены.
- Поля прибыли включены в автосохранение и восстановление черновика.

## [CURRENT] Тестовое покрытие

На момент коммита `238ec35` тестов на `netProfitManualAmount`/`profitAmount`/`financeComment` не существует (проверено: `grep` по этим именам в `*.test.ts` — ноль совпадений). Это не расхождение с намерением — `vitest.config.ts` в принципе ограничивает тесты чистыми функциями, а не server actions/UI, поэтому отсутствие тестов на server-action уровне ожидаемо в текущей архитектуре тестирования проекта.

## [TARGET] Будущее тестовое покрытие (требование, не текущее состояние)

Минимальный набор сценариев для БУДУЩЕГО добавления тестов чистых частей этой логики:
1. выручка 40 000 / прибыль 0;
2. положительная прибыль;
3. отрицательная прибыль;
4. отсутствующая прибыль отличима от нулевой;
5. приоритет выручки связанного `ScheduleEvent`;
6. исключение отменённого заказа;
7. правки выручки не меняют прибыль;
8. финансовый комментарий остаётся внутренним (не попадает в клиентский вывод);
9. дашборд использует один общий агрегат, а не JSX-арифметику.
