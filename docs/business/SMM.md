# SMM.md — раздел «SMM» (ведение соцсетей клиентов студии)

## [CURRENT] Назначение и место в архитектуре

SMM — новый раздел платформы (2026-08-08, первый этап), управляющий ведением соцсетей клиентов студии (Diamed, Виктор Пастернак, Алексей Зубов, Algisvet, Токмебель и т.д.). Центральная сущность — **SMM-проект клиента** (`SmmProject`): SMM НЕ создаёт вторых Client/Order/ScheduleEvent/User — расширяет их (`AGENTS.md`, п.1/4/11). Навигация: `SMM → Клиенты → карточка SMM-проекта конкретного клиента → вкладки` (Обзор/Пакет/Контент/Съёмки/Материалы/Команда/Финансы) — одна сущность-проект, а не семь независимых страниц.

**[RULE]** Это первый функциональный этап, не макет — весь описанный ниже функционал реально работает end-to-end (создание проекта → пакет → контент → съёмки → материалы → команда → финансы → выплаты → дашборд), проверено вручную по 4 сценариям (создание проекта Diamed-типа с пакетом и командой; съёмка контента → работа монтажёра → подтверждение → выплата; плановый платёж клиента → фактическая оплата → обновление дашборда; привязка существующей записи расписания клиента и открытие её карточки заказа).

## [CURRENT] Модели и владение

Все SMM-модели — `@@map("cms_smm_...")`, `smmProjectId` с `onDelete: Cascade` (кроме двух `@unique` реверс-связей ниже).

- **`SmmProject`** — `clientId → Client` (НЕ уникально: у клиента может быть несколько SMM-проектов за историю, повторное создание активного требует `confirmDuplicateForClient`, тот же приём, что `MontageProject.confirmDuplicateForOrder`, см. `MONTAGE.md`). `monthlyFee` — редактируемое поле, ничего не хардкодится по конкретным клиентам. `billingPeriodType: CALENDAR_MONTH | CUSTOM` + `startDate` — см. «Расчётный период» ниже. `responsibleManagerId`/участники — не отдельные поля на проекте, а через `SmmProjectMember` (см. «Команда»).
- **`SmmPackageItem`** — универсальный конструктор пакета услуг, а НЕ фиксированные колонки (`reelsCount` и т.п. сознательно не существуют). `serviceType` — словарь (`SHORT_VIDEO`, `LONG_VIDEO`, `POST`, `STORY`, `STUDIO_SHOOT`, `LOCATION_SHOOT`, `SHOOTING_HOURS`, `CONTENT_PLAN`, `PUBLICATION`, `DESIGN`, `OTHER` + `customName` для произвольного). `quantity` — **nullable**: заполнено → в UI дробь `done/target`; `null` → пункт описывается только текстом (`description`), например «скидка 20% на доп. записи в студии» — не участвует в числовом прогрессе (проверено живьём: пункт «Скидка на студию» не показывает дробь).
- **`SmmContentItem`** — единица контента (один ролик/пост = одна строка). `editingProjectId: String? @unique → MontageProject` — связь с УЖЕ существующей системой монтажа (см. «Связь с монтажом» ниже), не вторая система. `scheduleEventId → ScheduleEvent` — какая съёмка дала материал. `indexCode` — рабочий индекс готового ролика (см. «Индексация» ниже), заполняется вручную на первом этапе.
- **`SmmMaterialLink`** — реестр ссылок (НЕ файловое хранилище, тот же принцип, что `Document`, см. `DOCUMENTS.md`), категории `SOURCE/SOURCE_SORTED/FINISHED_SHORT/FINISHED_LONG/GRAPHICS/DOCUMENT/OTHER`, опциональные `relatedContentId`/`relatedScheduleEventId`.
- **`SmmProjectMember`** — `userId → User`, роль **внутри проекта** (`OWNER/STRATEGIST/SMM_MANAGER/EDITOR/OTHER`) — не глобальная platform-роль (`Role` enum остаётся отдельным, см. `SECURITY.md`). `activeTo=null` — активное членство; выход из команды — простановка `activeTo`, не удаление строки (сохраняет историю «кто когда работал над проектом»).
- **`SmmWorkItem`** — выполненная работа исполнителя, основа выплат (см. «Почему WorkItem — отдельная сущность» ниже). `performerId → EditorProfile` (не `User` — переиспользован существующий паттерн «студийный работник, который может ещё не иметь логина», см. ниже). Два независимых статуса: `status` (`DRAFT/SUBMITTED/APPROVED/REJECTED` — сделана ли работа) и `paymentStatus` (`UNPAID/PLANNED/PAID` — оплачена ли), тот же принцип раздельных измерений, что пауза/статус монтажа (`MONTAGE.md`).
- **`SmmPayment`** — факт выплаты исполнителю, группирует 0..N `SmmWorkItem` (0 — для `SALARY`/`BONUS`, не привязанных к конкретной работе). `type: PIECEWORK/SALARY/BONUS/OTHER`.
- **`SmmClientPayment`** — плановый/фактический платёж клиента по проекту. `plannedDate`/`plannedAmount` отдельно от `actualDate`/`actualAmount` — план и факт никогда не путаются (тот же принцип, что «Месячная выручка SMM» vs «Получено в текущем месяце» на дашборде, см. ниже).
- **`SmmScheduleLink`** — `scheduleEventId: String @unique → ScheduleEvent` — связывает УЖЕ существующую запись расписания/заказ с SMM-проектом и конкретным расчётным периодом; НЕ копирует поля заказа (дата/тип/длительность читаются через `scheduleEvent`, не дублируются).

### Реверс-связи в существующих моделях
`Client.smmProjects[]`; `User.smmProjectMemberships[]/smmContentResponsibleFor[]/smmMaterialLinksCreated[]/smmWorkItemsCreated[]/smmPaymentsCreated[]`; `EditorProfile.smmContentItems[]/smmWorkItems[]/smmPayments[]`; `MontageProject.smmContentItem?/smmWorkItems[]`; `ScheduleEvent.smmContentItems[]/smmMaterialLinks[]/smmScheduleLink?`.

## [RULE] Почему `performerId` — `EditorProfile`, не `User`

Платформа уже использует `EditorProfile` как «студийный работник, который может ещё не иметь аккаунта на платформе» (nullable `EditorProfile.userId`, обязательный `displayName`) — тот же паттерн монтажёров. SMM переиспользует его для исполнителей работ вместо создания параллельной сущности профиля (`AGENTS.md`, п.1/11). `SmmProjectMember.userId`, наоборот, — обязательно `User`, потому что роль в команде проекта («Владелец», «Стратегический SMM-менеджер» и т.п.) осмысленна только для человека с местом в платформе, а не для внешнего монтажёра-исполнителя.

## [CURRENT] Расчётный период (не всегда календарный месяц)

`computeSmmBillingPeriod` (`smm-model.ts`) — вычисляется на лету, не хранится построчно (тот же принцип, что `computeMontageDeadline`, `MONTAGE.md`). `CALENDAR_MONTH` — 1 число – последний день месяца. `CUSTOM` — якорь берётся из дня месяца `SmmProject.startDate`; если в текущем месяце этот день ещё не наступил, период считается начавшимся в прошлом календарном месяце. Проверено живьём на реальном примере из ТЗ: старт 08.08.2026 → период «8 августа 2026 г. – 7 сентября 2026 г.» посимвольно совпал с примером задания.

## [CURRENT] Прогресс пакета — вычисляется, не хранится

`computePackageProgress` (`smm-model.ts`) — для каждого `SmmPackageItem` с `included=true` считает число `SmmContentItem` того же `serviceType`, статус ≠ `CANCELLED`, чья `plannedPublishDate` (или `createdAt`, если дата публикации не указана) попадает в текущий расчётный период. Пункты пакета без числового `quantity` не участвуют в дроби — показываются только описанием. Проверено живьём: создание двух `SmmContentItem` типа `SHORT_VIDEO` подняло фракцию на карточке проекта с «0 / 25 шт.» до «2 / 25 шт.».

## [CURRENT] Статусы контента (10 значений, этап 1)

`IDEA → PLANNED → WAITING_FOR_SHOOT → SHOT → IN_EDIT → REVIEW → APPROVED → SCHEDULED → PUBLISHED`, `CANCELLED` — терминальный вне потока (`SMM_CONTENT_STATUS_ORDER`, тот же принцип, что `MONTAGE_STATUS_ORDER`). Русские лейблы — `SMM_CONTENT_STATUS_LABELS`.

## [RULE] Связь с монтажом — расширение существующей системы, не вторая

`SmmContentItem.editingProjectId` (`@unique → MontageProject`) — `linkSmmContentToMontage` вызывает УЖЕ существующий `createMontageProject` (`actions/montage.ts`) напрямую, без `orderId` (SMM-контент часто не привязан к конкретному заказу). Статус монтажа и ссылка на готовый файл читаются ЧЕРЕЗ реальный `MontageProject` (`editingProjectStatus`/`editingProjectDeliveryUrl` на DTO вычисляются при построении, не копируются в отдельные поля) — нет двух мест правды для одного и того же ролика (тот же принцип, что `ORDERS.md`/`MONTAGE.md` требуют для остальной платформы).

## [CURRENT] Индексация готовых роликов

`SmmContentItem.indexCode` — свободное текстовое поле, ручной ввод на этапе 1 (формат вида `DIA-2026.08.08-AH-017`: клиент/дата/инициалы монтажёра/порядковый номер — соглашение студии, не enforced кодом). **[TARGET]** Автогенерация индекса — будущий этап (см. «Что отложено» ниже), поле уже существует, чтобы не потребовалась миграция схемы при добавлении автогенерации.

## [RULE] Съёмки — привязка существующих записей, не новый календарь

`SmmScheduleLink` не создаёт вторую систему бронирования — связывает уже существующую `ScheduleEvent`/`Order` с SMM-проектом. Вкладка «Съёмки» показывает только записи выбранного клиента, ещё не привязанные ни к одному SMM-проекту (`getUnlinkedScheduleEventsForClient`). «Открыть заказ» открывает РЕАЛЬНУЮ карточку заказа (`EventCardModal` в `/admin/crm`) через `?openOrderId=` — параметр, который `OrdersBoard.tsx` считывает в `useEffect` при монтаже и открывает тот же `EventCardModal`, что и обычный клик по карточке доски (не отдельная облегчённая карточка для SMM — тот же компонент, тот же `buildVmFromOrder`, см. `AGENTS.md`, «Редактируемость связанных сущностей», п.3). Добавлено 2026-08-08 при живой проверке сценария 4 — до этого ссылка вела на голый `/admin/crm` без auto-open, что не соответствовало ТЗ п.15 («строка должна открывать существующую карточку заказа»).

## [RULE] Почему `SmmWorkItem` — отдельная сущность, а не поле на `SmmContentItem`

Один ролик может потребовать несколько отдельно оплачиваемых работ (монтаж 1500₽ + субтитры 300₽ + правки 500₽), и наоборот — не каждая работа привязана к конкретному ролику (`contentItemId` nullable). Хранить оплату прямо на `SmmContentItem` сделало бы невозможным и то, и другое. Архитектура рассчитана на будущий кабинет монтажёра (см. «Что отложено»): монтажёр сам выбирает клиента, фиксирует работу, прикладывает готовый файл/индекс, отправляет на подтверждение — сейчас это делает от его имени SMM-менеджер/владелец.

## [CURRENT] Выплаты — «К выплате» → «Отметить выплаченным» → «История выплат»

`createSmmPayment` (`actions/smm.ts`) — в одной `prisma.$transaction`: считает сумму из выбранных `APPROVED`+`UNPAID` `SmmWorkItem` (или берёт явный `amount` для `SALARY`/`BONUS`), создаёт `SmmPayment`, переводит выбранные `SmmWorkItem` в `paymentStatus=PAID`+`paymentId` — исключает состояние «выплата создана, а работа осталась висеть в "К выплате"» (тот же класс защиты, что append-only аудит в `DATA_SAFETY.md`, но здесь — атомарность одной операции, а не неизменяемость истории). Раздел «Выплаты» группирует неоплаченное `APPROVED` по исполнителю; «История выплат» разворачивается и показывает состав (какие именно работы вошли).

## [CURRENT] Дашборд — план не путается с фактом

«Месячная выручка SMM» = сумма `monthlyFee` активных проектов (`computeSmmMonthlyRevenue`, `smm-model.ts`) — плановая величина. «Получено в текущем месяце» = сумма фактических `SmmClientPayment.actualAmount` с `actualDate` в текущем месяце — реально зарегистрированные оплаты. Эти две цифры сознательно не смешиваются в одну (тот же принцип, что `FINANCE.md` требует для «Прибыли по заказу»: план ≠ факт). Проверено живьём: до фактической отметки оплаты «Ожидается от клиентов» показывало 92 500 ₽, «Получено» — 0 ₽; после `markSmmClientPaymentPaid` — ровно наоборот.

## [CURRENT] Роли и права (этап 1)

Проверка — стандартная сессия сотрудника (`requireStaffSession()`, локальный helper в `actions/smm.ts`, тот же паттерн copy-paste, что в `orders.ts`/`clients.ts`/`montage.ts` — см. `SECURITY.md`). **[CURRENT]** Тонкого RBAC внутри SMM нет — любой сотрудник с доступом в админку может видеть/редактировать любой SMM-проект; `SmmProjectMember`-роли (`OWNER/STRATEGIST/...`) сейчас описательные (кто есть кто в команде проекта), не enforced как permission-барьер. Это осознанное ограничение этапа 1 (см. `SECURITY.md`, «Известные ограничения RBAC» — та же формулировка применена и здесь), а не забытая задача.

**[RULE] `createdById`-поля обязаны идти через `resolveValidUserId`, не напрямую из `session.user.id`.** Найдено и исправлено 2026-08-08 при живом тестировании сценария 2: `addSmmMaterialLink`/`createSmmWorkItem`/`createSmmPayment` изначально писали `createdById: authResult.userId` напрямую — под протухшей/несовпадающей сессией (`session.user.id`, не совпадающий ни с одной строкой `User`, см. `audit.ts`, тот же класс проблемы, что и системный баг `writeAuditLog` 2026-07-22) это падало на FK-constraint (`P2003`), ошибка тихо превращалась в общий текст «Не удалось добавить...» без указания причины. Исправлено — все три места резолвят `createdById` через `resolveValidUserId(prisma \| tx, authResult.userId)` перед записью, как и остальная платформа.

## [CURRENT] Что реализовано на этапе 1 (полный список экранов)

`SMM` (хаб): Обзор (дашборд с KPI + «Ближайшие платежи клиентов»/«Ближайшие выплаты команде»/«Проблемные задачи»), Клиенты (список SMM-проектов + создание нового), Контент (сквозной список по всем проектам), Выплаты («К выплате» + «История выплат»), Команда (список сотрудников + создание). Карточка SMM-проекта (`/admin/smm/[projectId]`): Обзор, Пакет (конструктор), Контент (создание/редактирование единиц + встроенное «+ работа» + «В монтаж»), Съёмки (привязка/отвязка записей расписания), Материалы (реестр ссылок), Команда (назначение/снятие участников), Финансы (плановые/фактические платежи клиента).

## [TARGET] Что сознательно отложено на будущие этапы

Не потому что забыто — потому что ТЗ явно исключило это из этапа 1 (см. также «Роли и права» выше):
1. Полноценный календарь контент-плана (сейчас — таблица; данные уже готовы для календарного отображения, `plannedPublishDate`/`deadline` на каждой единице).
2. Миграция существующих Google Sheets клиентских отчётов.
3. Аналитика просмотров/охватов соцсетей (ручной/автоматический сбор).
4. Личный кабинет монтажёра (модель уже это допускает — см. «Почему WorkItem — отдельная сущность»).
5. Личный кабинет клиента (что можно/нельзя показывать клиенту продумано на уровне DTO — внутренние суммы выплат исполнителям НИКОГДА не должны попасть в клиентский API, если/когда он появится).
6. Автогенерация `indexCode` (поле уже есть, заполняется вручную).
7. Уведомления (просроченный контент/платежи — пока видны только на дашборде, не пушатся).
8. `SmmRecurringPayout` — регулярные фиксированные выплаты (зарплата) с повторяющимся расписанием («50 000₽ 15 числа», «50% 10-го / 50% 25-го») — модель `SmmPayment.type=SALARY` уже позволяет создавать ручные выплаты этого типа, но механизма автогенерации по расписанию нет.
9. Аналитика рентабельности по SMM-клиенту (сравнение `monthlyFee` с суммой реально выплаченных `SmmWorkItem` по проекту) — данные для неё уже связаны в схеме, отдельного отчёта пока нет.
