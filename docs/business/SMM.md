# SMM.md — раздел «SMM» (ведение соцсетей клиентов студии)

## [CURRENT] Назначение и место в архитектуре

SMM — новый раздел платформы (2026-08-08, первый этап), управляющий ведением соцсетей клиентов студии (Diamed, Виктор Пастернак, Алексей Зубов, Algisvet, Токмебель и т.д.). Центральная сущность — **SMM-проект клиента** (`SmmProject`): SMM НЕ создаёт вторых Client/Order/ScheduleEvent/User — расширяет их (`AGENTS.md`, п.1/4/11). Навигация: `SMM → Клиенты → карточка SMM-проекта конкретного клиента → вкладки` (Обзор/Пакет/Контент/Съёмки/Материалы/Команда/Финансы) — одна сущность-проект, а не семь независимых страниц.

**[RULE]** Это первый функциональный этап, не макет — весь описанный ниже функционал реально работает end-to-end (создание проекта → пакет → контент → съёмки → материалы → команда → финансы → выплаты → дашборд), проверено вручную по 4 сценариям (создание проекта Diamed-типа с пакетом и командой; съёмка контента → работа монтажёра → подтверждение → выплата; плановый платёж клиента → фактическая оплата → обновление дашборда; привязка существующей записи расписания клиента и открытие её карточки заказа).

**[CURRENT] Этап 2A (2026-08-09) — архитектурное расширение модели производства контента.** Аудит реальных рабочих SMM-таблиц студии (Diamed, TOK, ЗубовЛаб, AlgisVet) после этапа 1 выявил, что «единица контента» и «публикация в соцсети» — разные понятия (один ролик может быть одновременно опубликован в Instagram/Telegram/VK/YouTube, у каждой публикации своя дата/URL/статус/метрики). Модель расширена до `SmmProject → SmmContentItem → SmmPublication → SmmPublicationMetric`, добавлены many-to-many `ContentItem ↔ ScheduleEvent`, parent/child `ContentItem`, типизация материалов, разделение Source/Master/Publication URL. Это подготовительный архитектурный этап перед будущим разделом «Производство» (2B) — сознательно НЕ включает большой новый UI, календарь, кабинеты клиента/монтажёра или аналитику (см. «Отложено на 2B» в конце документа). Проверено на реальном тестовом сценарии по ТЗ (создание Д186-подобного ролика, 3 съёмки, 4 публикации, снапшоты метрик, parent/child, cycle-protection) — см. «Что реализовано в 2A» ниже.

## [CURRENT] Модели и владение

Все SMM-модели — `@@map("cms_smm_...")`, `smmProjectId` с `onDelete: Cascade` (кроме двух `@unique` реверс-связей ниже).

- **`SmmProject`** — `clientId → Client` (НЕ уникально: у клиента может быть несколько SMM-проектов за историю, повторное создание активного требует `confirmDuplicateForClient`, тот же приём, что `MontageProject.confirmDuplicateForOrder`, см. `MONTAGE.md`). `monthlyFee` — редактируемое поле, ничего не хардкодится по конкретным клиентам. `billingPeriodType: CALENDAR_MONTH | CUSTOM` + `startDate` — см. «Расчётный период» ниже. `responsibleManagerId`/участники — не отдельные поля на проекте, а через `SmmProjectMember` (см. «Команда»).
- **`SmmPackageItem`** — универсальный конструктор пакета услуг, а НЕ фиксированные колонки (`reelsCount` и т.п. сознательно не существуют). `serviceType` — словарь (`SHORT_VIDEO`, `LONG_VIDEO`, `POST`, `STORY`, `STUDIO_SHOOT`, `LOCATION_SHOOT`, `SHOOTING_HOURS`, `CONTENT_PLAN`, `PUBLICATION`, `DESIGN`, `OTHER` + `customName` для произвольного). `quantity` — **nullable**: заполнено → в UI дробь `done/target`; `null` → пункт описывается только текстом (`description`), например «скидка 20% на доп. записи в студии» — не участвует в числовом прогрессе (проверено живьём: пункт «Скидка на студию» не показывает дробь).
- **`SmmContentItem`** — единица ПРОИЗВЕДЁННОГО контента (один ролик/пост/карусель = одна строка), НЕ публикация и НЕ строка аналитики (см. «Content vs Publication» ниже). `editingProjectId: String? @unique → MontageProject` — связь с УЖЕ существующей системой монтажа (см. «Связь с монтажом» ниже), не вторая система. `contentCode` — постоянный человекочитаемый бизнес-идентификатор («Д186», см. «Content Code» ниже). `productionBrief` — свободнотекстовое ТЗ исполнителю, отдельно от `description` (идея/концепция материала). `parentContentId` — self-relation для связки «длинный выпуск → тизер/фрагменты» (см. «Parent/child» ниже). **[DEPRECATED, 2A]** `scheduleEventId`/`sourceUrl`/`resultUrl`/`publishedUrl` оставлены не удалёнными ради обратной совместимости, новый код их не пишет (см. «Content ↔ ScheduleEvent» и «Source/Master/Publication URL» ниже).
- **`SmmPublication`** (2A) — публикация единицы контента на конкретной площадке (`SmmPublicationPlatform: INSTAGRAM/TELEGRAM/VK/YOUTUBE/RUTUBE/OTHER` + `customPlatform`), 1 `ContentItem` → 0..N `Publication`. Свой `status` (`PLANNED/READY/PUBLISHED/CANCELLED`), независимый от production-статуса `ContentItem`. `plannedPublishAt`/`publishedAt` — раздельные поля (план ≠ факт, тот же принцип, что `SmmClientPayment`). `onDelete: Cascade` от `ContentItem`.
- **`SmmPublicationMetric`** (2A) — снимок показателя публикации (`metricType: VIEWS/REACH/LIKES/COMMENTS/SHARES/SAVES/REACTIONS/FOLLOWERS_GAINED/RETENTION_PERCENT/WATCH_TIME`, `value`, `capturedAt`, `source: MANUAL/API/IMPORT`). Нормализованная модель (одна метрика = одна строка), а не набор nullable-колонок на `Publication` — см. «Метрики» ниже.
- **`SmmContentScheduleLink`** (2A) — many-to-many `ContentItem ↔ ScheduleEvent` (`@@unique([contentItemId, scheduleEventId])`). НЕ то же самое, что `SmmScheduleLink` ниже — см. «Content ↔ ScheduleEvent».
- **`SmmMaterialLink`** — реестр ссылок (НЕ файловое хранилище, тот же принцип, что `Document`, см. `DOCUMENTS.md`), категории `SOURCE/SOURCE_SORTED/FINISHED_SHORT/FINISHED_LONG/GRAPHICS/DOCUMENT/OTHER`, опциональные `relatedContentId`/`relatedScheduleEventId`. **[CURRENT, 2A]** `materialType` (nullable, `SOURCE_VIDEO/SOURCE_AUDIO/SELECTED_SOURCE/MASTER/COVER/REFERENCE/DOCUMENT/IMAGE/OTHER`) добавлен поверх `category` для более гранулярной типизации — не замена, `category` продолжает нести прежний смысл (см. «Материалы — типизация» ниже).
- **`SmmProjectMember`** — `userId → User`, роль **внутри проекта** (`OWNER/STRATEGIST/SMM_MANAGER/EDITOR/OTHER`) — не глобальная platform-роль (`Role` enum остаётся отдельным, см. `SECURITY.md`). `activeTo=null` — активное членство; выход из команды — простановка `activeTo`, не удаление строки (сохраняет историю «кто когда работал над проектом»).
- **`SmmWorkItem`** — выполненная работа исполнителя, основа выплат (см. «Почему WorkItem — отдельная сущность» ниже). `performerId → EditorProfile` (не `User` — переиспользован существующий паттерн «студийный работник, который может ещё не иметь логина», см. ниже). Два независимых статуса: `status` (`DRAFT/SUBMITTED/APPROVED/REJECTED` — сделана ли работа) и `paymentStatus` (`UNPAID/PLANNED/PAID` — оплачена ли), тот же принцип раздельных измерений, что пауза/статус монтажа (`MONTAGE.md`).
- **`SmmPayment`** — факт выплаты исполнителю, группирует 0..N `SmmWorkItem` (0 — для `SALARY`/`BONUS`, не привязанных к конкретной работе). `type: PIECEWORK/SALARY/BONUS/OTHER`.
- **`SmmClientPayment`** — плановый/фактический платёж клиента по проекту. `plannedDate`/`plannedAmount` отдельно от `actualDate`/`actualAmount` — план и факт никогда не путаются (тот же принцип, что «Месячная выручка SMM» vs «Получено в текущем месяце» на дашборде, см. ниже).
- **`SmmScheduleLink`** — `scheduleEventId: String @unique → ScheduleEvent` — связывает УЖЕ существующую запись расписания/заказ с SMM-проектом и конкретным расчётным периодом; НЕ копирует поля заказа (дата/тип/длительность читаются через `scheduleEvent`, не дублируются).

### Реверс-связи в существующих моделях
`Client.smmProjects[]`; `User.smmProjectMemberships[]/smmContentResponsibleFor[]/smmMaterialLinksCreated[]/smmWorkItemsCreated[]/smmPaymentsCreated[]/smmPublicationMetricsCreated[]`; `EditorProfile.smmContentItems[]/smmWorkItems[]/smmPayments[]`; `MontageProject.smmContentItem?/smmWorkItems[]`; `ScheduleEvent.smmContentItems[]/smmMaterialLinks[]/smmScheduleLink?/smmContentScheduleLinks[]`.

## [RULE] Content vs Publication (2A) — главное разделение этапа

Один ролик может быть опубликован одновременно в Instagram, Telegram, VK и YouTube — это ОДИН `SmmContentItem`, но ЧЕТЫРЕ `SmmPublication` (SMM.md, аудит рабочих таблиц). У каждой публикации своя площадка/плановая дата/фактическая дата/URL/статус/метрики — хранить это одним набором полей на `ContentItem` было архитектурно некорректно (что и обнаружил аудит: `plannedPublishDate`/`publishedUrl` этапа 1 могли описать только ОДНУ публикацию, хотя реальных клиентов студии публикуют один и тот же материал на нескольких площадках). **Важно:** количество `Publication` НИКОГДА не влияет на выполнение пакета — `computePackageProgress` считает `ContentItem`, не итерирует `Publication` вообще (её сигнатура их даже не принимает на вход) — 18 роликов на 4 площадках = 18 единиц выполнения пакета, не 72 (см. regression-тест в `smm-model.test.ts`).

## [CURRENT] Content type vs Package service type (2A)

`SmmContentItem.serviceType` и `SmmPackageItem.serviceType` продолжают использовать ОДИН И ТОТ ЖЕ enum `SmmServiceType` (не форкнуты на два словаря) — иначе `computePackageProgress` потребовал бы явного маппинга между двумя параллельными наборами значений вместо прямого сравнения. Enum расширен аддитивно: `+CAROUSEL`, `+TEASER` (существующие значения не удалены/не переименованы — безопасно для уже сохранённых `SmmPackageItem`). Разделение сделано на уровне UI: `CONTENT_SERVICE_TYPES` (`smm-model.ts`) — подмножество, которое реально показывается в форме единицы контента (`SHORT_VIDEO/LONG_VIDEO/POST/CAROUSEL/STORY/TEASER/OTHER`); `STUDIO_SHOOT/LOCATION_SHOOT/SHOOTING_HOURS/CONTENT_PLAN/PUBLICATION/DESIGN` остаются в общем enum (нужны `SmmPackageItem` — это договорные понятия пакета), но не предлагаются как формат произведённого контента.

## [CURRENT] Content Code vs File/Editing Code (2A)

`SmmContentItem.contentCode` (Prisma-поле переименовано из `indexCode`, физическая колонка `index_code` не тронута — переименование через `@map`, без миграции данных) — постоянный человекочитаемый БИЗНЕС-идентификатор единицы контента («Д186», «ЗЛ1», «А1», «П1» — реальные префиксы клиентов студии), не индекс файла монтажёра. Это разные сущности: Content Code — «Д186» (присваивается единожды, живёт с единицей контента всегда), File/Editing Code — «2026.08.09-AH-017» (дата + инициалы монтажёра + порядковый номер, соглашение студии для готовых файлов, пока вводится вручную через `SmmWorkItem`/материалы, не отдельное поле). Не смешиваются в одном поле.

## [CURRENT] Метрики публикации — снимки истории, не последнее значение (2A)

`SmmPublicationMetric` — каждый ввод показателя добавляет НОВУЮ строку с `capturedAt`, никогда не перезаписывает существующую (10.08 → 12000 просмотров, 17.08 → 18400, 31.08 → 25100 — все три строки сохраняются). `getLatestMetricByType` (`smm-model.ts`, чистая функция) вычисляет последнее значение по каждому `metricType` для компактного отображения в UI — история при этом не теряется, доступна в развёрнутом виде. `source` сейчас всегда `MANUAL` (ручной ввод); `API`/`IMPORT` зарезервированы под будущие этапы (автосбор через API соцсетей, историческая миграция таблиц) — не подключаются в 2A.

## [RULE] Content ↔ ScheduleEvent — many-to-many, не путать со SmmScheduleLink (2A)

Одна съёмка может породить несколько единиц контента (одна смена Diamed → Д186, Д187, Д188, Д189), поэтому `SmmContentScheduleLink` — полноценная many-to-many таблица, НЕ переиспользование `SmmScheduleLink`. Это две принципиально разные сущности с разной кардинальностью: `SmmScheduleLink` уникален по `scheduleEventId` — привязывает СЪЁМКУ ЦЕЛИКОМ к ОДНОМУ SMM-ПРОЕКТУ (для вкладки «Съёмки»/выполнения пакета, этап 1); `SmmContentScheduleLink` связывает КОНКРЕТНУЮ ЕДИНИЦУ КОНТЕНТА с КОНКРЕТНОЙ съёмкой, одна съёмка легитимно связана сразу с несколькими `ContentItem`, и наоборот. Обнаружено при аудите: изначальный (этап 1) `SmmContentItem.scheduleEventId` был одиночной связью и НИКОГДА не имел UI для редактирования (мёртвое поле на практике) — заменён на `scheduleLinks`, колонка оставлена в схеме как `[DEPRECATED]`. **Миграционная стратегия:** на момент начала 2A прямым запросом к БД подтверждено 0 строк `SmmContentItem` в проде (модуль ещё не использовался для реальной работы) — переносить нечего, backfill-скрипт не потребовался; колонка и обратная связь `ScheduleEvent.smmContentItems[]` оставлены нетронутыми на случай, если какой-то будущий импорт всё же захочет писать в старую форму, но новый код читает/пишет ТОЛЬКО через `scheduleLinks`.

## [CURRENT] Parent/child Content (2A)

`SmmContentItem.parentContentId` — self-relation (длинный выпуск → тизер/фрагменты, `Podcast #12 → Short #1/#2/#3, Teaser`), НЕ отдельные модели `Teaser`/`Clip`/`LongVideo` — это всё `ContentItem` разных `serviceType`. `onDelete: SetNull` — удаление родителя НЕ каскадно стирает дочерние ролики, они просто остаются без родителя (это данные о произведённом контенте, они не должны исчезать вслед за карточкой родителя). Защита от циклов — `wouldCreateContentParentCycle` (`smm-model.ts`, чистая функция, покрыта тестами: self-reference `A→A`, короткий цикл `A→B→A`, длинный `A→B→C→A`) — НЕ общий graph engine, просто обход цепочки родителей нового `parentContentId` вверх с ограничением глубины (защита от уже испорченных данных, не ожидаемый рабочий кейс). Вызывается на сервере (`updateSmmContentItem`) перед записью; на `create` цикл невозможен по определению (у новой строки ещё нет id, на который мог бы ссылаться существующий родитель).

## [CURRENT] Материалы — типизация (2A)

`SmmMaterialLink.materialType` (nullable) добавлен ПОВЕРХ существующей `category`, не заменяет её: `category` — укрупнённая корзина этапа 1 (уже используется фильтрами вкладки «Материалы»), `materialType` — что это физически за файл (`SOURCE_VIDEO/SOURCE_AUDIO/SELECTED_SOURCE/MASTER/COVER/REFERENCE/DOCUMENT/IMAGE/OTHER`). Существующие строки не требуют заполнения задним числом. Форма вкладки «Материалы» также получила выбор конкретной единицы контента (`relatedContentId` — поле существовало с этапа 1, но не имело UI до 2A).

## [RULE] Source/Master/Publication URL — три разных смысла (2A)

- **Source URL** (материалы для производства) — `SmmMaterialLink` с `category=SOURCE`/`materialType=SOURCE_VIDEO|SOURCE_AUDIO`, привязанный к `ContentItem` через `relatedContentId`.
- **Master URL** (готовый произведённый файл) — приоритетно `editingProjectDeliveryUrl` (реальный `MontageProject.deliveryUrl`, если контент передан монтажёру — MontageProject остаётся source of truth, см. ниже), иначе `SmmMaterialLink` с `materialType=MASTER`.
- **Publication URL** (ссылка на опубликованный материал в конкретной соцсети) — ТОЛЬКО `SmmPublication.url`, по одной строке на каждую площадку.

`SmmContentItem.sourceUrl`/`resultUrl`/`publishedUrl` (этап 1) помечены `[DEPRECATED]` в схеме и коде — физически не удалены (обратная совместимость, данные безопасности), но новый UI их больше не показывает и не пишет.

## [RULE] Почему `performerId` — `EditorProfile`, не `User`

Платформа уже использует `EditorProfile` как «студийный работник, который может ещё не иметь аккаунта на платформе» (nullable `EditorProfile.userId`, обязательный `displayName`) — тот же паттерн монтажёров. SMM переиспользует его для исполнителей работ вместо создания параллельной сущности профиля (`AGENTS.md`, п.1/11). `SmmProjectMember.userId`, наоборот, — обязательно `User`, потому что роль в команде проекта («Владелец», «Стратегический SMM-менеджер» и т.п.) осмысленна только для человека с местом в платформе, а не для внешнего монтажёра-исполнителя.

## [CURRENT] Расчётный период (не всегда календарный месяц)

`computeSmmBillingPeriod` (`smm-model.ts`) — вычисляется на лету, не хранится построчно (тот же принцип, что `computeMontageDeadline`, `MONTAGE.md`). `CALENDAR_MONTH` — 1 число – последний день месяца. `CUSTOM` — якорь берётся из дня месяца `SmmProject.startDate`; если в текущем месяце этот день ещё не наступил, период считается начавшимся в прошлом календарном месяце. Проверено живьём на реальном примере из ТЗ: старт 08.08.2026 → период «8 августа 2026 г. – 7 сентября 2026 г.» посимвольно совпал с примером задания.

## [CURRENT] Прогресс пакета — вычисляется, не хранится

`computePackageProgress` (`smm-model.ts`) — для каждого `SmmPackageItem` с `included=true` считает число `SmmContentItem` того же `serviceType`, статус ≠ `CANCELLED`, чья `plannedPublishDate` (или `createdAt`, если дата публикации не указана) попадает в текущий расчётный период. Пункты пакета без числового `quantity` не участвуют в дроби — показываются только описанием. Проверено живьём: создание двух `SmmContentItem` типа `SHORT_VIDEO` подняло фракцию на карточке проекта с «0 / 25 шт.» до «2 / 25 шт.».

## [CURRENT] Статусы контента (10 значений, этап 1)

`IDEA → PLANNED → WAITING_FOR_SHOOT → SHOT → IN_EDIT → REVIEW → APPROVED → SCHEDULED → PUBLISHED`, `CANCELLED` — терминальный вне потока (`SMM_CONTENT_STATUS_ORDER`, тот же принцип, что `MONTAGE_STATUS_ORDER`). Русские лейблы — `SMM_CONTENT_STATUS_LABELS`.

## [RULE] Связь с монтажом — расширение существующей системы, не вторая

`SmmContentItem.editingProjectId` (`@unique → MontageProject`) — `linkSmmContentToMontage` вызывает УЖЕ существующий `createMontageProject` (`actions/montage.ts`) напрямую, без `orderId` (SMM-контент часто не привязан к конкретному заказу). Статус монтажа и ссылка на готовый файл читаются ЧЕРЕЗ реальный `MontageProject` (`editingProjectStatus`/`editingProjectDeliveryUrl` на DTO вычисляются при построении, не копируются в отдельные поля) — нет двух мест правды для одного и того же ролика (тот же принцип, что `ORDERS.md`/`MONTAGE.md` требуют для остальной платформы).

## [RULE] Съёмки — привязка существующих записей, не новый календарь

`SmmScheduleLink` не создаёт вторую систему бронирования — связывает уже существующую `ScheduleEvent`/`Order` с SMM-проектом. Вкладка «Съёмки» показывает только записи выбранного клиента, ещё не привязанные ни к одному SMM-проекту (`getUnlinkedScheduleEventsForClient`). «Открыть заказ» открывает РЕАЛЬНУЮ карточку заказа (`EventCardModal` в `/admin/crm`) через `?openOrderId=` — параметр, который `OrdersBoard.tsx` считывает в `useEffect` при монтаже и открывает тот же `EventCardModal`, что и обычный клик по карточке доски (не отдельная облегчённая карточка для SMM — тот же компонент, тот же `buildVmFromOrder`, см. `AGENTS.md`, «Редактируемость связанных сущностей», п.3). Добавлено 2026-08-08 при живой проверке сценария 4 — до этого ссылка вела на голый `/admin/crm` без auto-open, что не соответствовало ТЗ п.15 («строка должна открывать существующую карточку заказа»).

## [RULE] Почему `SmmWorkItem` — отдельная сущность, а не поле на `SmmContentItem`

Один ролик может потребовать несколько отдельно оплачиваемых работ (монтаж 1500₽ + субтитры 300₽ + правки 500₽), и наоборот — не каждая работа привязана к конкретному ролику (`contentItemId` nullable). Хранить оплату прямо на `SmmContentItem` сделало бы невозможным и то, и другое. Архитектура рассчитана на будущий кабинет монтажёра (см. «Что отложено»): монтажёр сам выбирает клиента, фиксирует работу, прикладывает готовый файл/индекс, отправляет на подтверждение — сейчас это делает от его имени SMM-менеджер/владелец.

## [CURRENT] Выплаты — «К выплате» → «Отметить выплаченным» → «История выплат»

`createSmmPayment` (`actions/smm.ts`) — в одной `prisma.$transaction`: считает сумму из выбранных `APPROVED`+`UNPAID` `SmmWorkItem` (или берёт явный `amount` для `SALARY`/`BONUS`), создаёт `SmmPayment`, переводит выбранные `SmmWorkItem` в `paymentStatus=PAID`+`paymentId` — исключает состояние «выплата создана, а работа осталась висеть в "К выплате"» (тот же класс защиты, что append-only аудит в `DATA_SAFETY.md`, но здесь — атомарность одной операции, а не неизменяемость истории). Раздел «Выплаты» группирует неоплаченное `APPROVED` по исполнителю; «История выплат» разворачивается и показывает состав (какие именно работы вошли).

## [CURRENT] Дашборд — план не путается с фактом

«Месячная выручка SMM» = сумма `monthlyFee` активных проектов (`computeSmmMonthlyRevenue`, `smm-model.ts`) — плановая величина. «Получено в текущем месяце» = сумма фактических `SmmClientPayment.actualAmount` с `actualDate` в текущем месяце — реально зарегистрированные оплаты. Эти две цифры сознательно не смешиваются в одну (тот же принцип, что `FINANCE.md` требует для «Прибыли по заказу»: план ≠ факт). Проверено живьём: до фактической отметки оплаты «Ожидается от клиентов» показывало 92 500 ₽, «Получено» — 0 ₽; после `markSmmClientPaymentPaid` — ровно наоборот.

**Источник данных — НЕ отдельная модель.** Production — чистая VIEW поверх уже существующих сущностей (Content=`SmmContentItem`, Съёмка=`ScheduleEvent`, Монтаж=`MontageProject`, Публикация=`SmmPublication`, Метрики=`SmmPublicationMetric`, Материал=`SmmMaterialLink`, Оплачиваемая работа=`SmmWorkItem`) — никаких `productionEditor`/`productionPublishedUrl`/второго статуса не заведено.

**Две независимые query/DTO-пары** (`actions/smm.ts`) — намеренно НЕ общий гигантский include:
- `getSmmProductionItems()` + `SmmProductionRowDTO` (`PRODUCTION_ROW_INCLUDE`) — лёгкий список для ВСЕЙ таблицы: только поля, реально нужные строке/фильтру (без `productionBrief`, без полных `MaterialLink`/`Publication`, без снимков метрик).
- `getSmmContentItemDetail(id)` + `SmmContentItemDetailDTO` (`CONTENT_ITEM_DETAIL_INCLUDE`) — полная карточка, запрашивается ПООДИНОЧКЕ только когда пользователь реально открывает конкретную единицу контента.

**Единая каноническая карточка — `SmmContentItemCard.tsx`** (`src/components/smm/`). Открывается ОДИНАКОВО из трёх мест: таблицы/канбана Production, вкладки «Контент» карточки SMM-проекта (`SmmProjectContentTab.tsx`), и по прямой ссылке `?openContentId=...` — везде один и тот же компонент, не три разных редактора. Карточка НЕ фетчит данные сама в эффекте (тот же принцип, что уже применялся к `?openOrderId=` в `OrdersBoard.tsx`, чтобы не повторить найденный ранее в этой сессии баг `react-hooks/set-state-in-effect`) — родитель асинхронно загружает `SmmContentItemDetailDTO` внутри click-обработчика (Production/вкладка «Контент») ИЛИ он уже резолвлен на сервере в `production/page.tsx` для deep-link, карточка только принимает готовые данные пропсами.

**Deep-link `?openContentId=...`** — резолвится СЕРВЕРНО в `production/page.tsx` (`getSmmContentItemDetail`) до первой отрисовки, тот же паттерн, что `?openOrderId=` в `admin/crm/page.tsx`. В отличие от `OrdersBoard.tsx` (который убирает параметр из URL сразу после монтирования), Production намеренно ДЕРЖИТ `openContentId` в адресной строке, пока карточка открыта — открытие/закрытие карточки и изменение фильтров обновляют URL синхронно внутри обработчиков событий (`router.replace`, без единого `useEffect` с `setState` внутри) — ссылку на конкретную единицу контента можно скопировать в любой момент.

**Таблица** (`ProductionTable.tsx`) — столбцы Код/Клиент/Контент/Формат/Статус (инлайн-select, сохраняет сразу через `updateSmmContentItem` + `router.refresh()`, без оптимистичного UI)/Публикация (ближайшая дата + число площадок)/Ответственный/Монтажёр/Монтаж (свёртка `MontageStatus` в 4 состояния, `getContentMontageShortState`)/Дедлайн/Материалы (компактно есть/нет исходников и мастера)/Просрочка. `SmmProductionRowDTO.editorId`/`editorName` — приоритет `editingProject.editor` (реальный монтаж) над pre-assignment `ContentItem.editorId` — то же правило, что уже используется в `MontageProjectsTable`.

**Канбан** (`ProductionKanban.tsx`) — колонки по `SMM_CONTENT_STATUS_ORDER`, компактные карточки, БЕЗ drag & drop в этой версии (смена статуса — через инлайн-select таблицы или карточку); DnD сознательно не добавлен, чтобы не увеличивать scope этапа (`SmmContentStatus` при этом не менялся — см. «Статусы контента» выше).

**Фильтры/пресеты/сортировка/KPI** — вся логика чистыми функциями в `smm-model.ts`, не размазана по компонентам: `filterSmmProductionRows` (клиент/статус/формат/монтажёр/площадка/дата/поиск/`readyToPublishOnly`), `matchesSmmProductionDateFilter` (Сегодня/Эта неделя/Этот месяц — календарные, понедельник-воскресенье/1-е—последнее число; Просрочено — читает уже посчитанный `isOverdue`, не пересчитывает даты второй раз; Без даты), `sortSmmProductionRowsDefault` (просроченные → ближайший дедлайн → ближайшая публикация → дата создания), `computeSmmProductionKpis` (В работе/Монтаж/На проверке/Готово к публикации/Просрочено). Быстрые пресеты («Сегодня»/«Просрочено»/«Нужно снять»/«Монтаж»/«На проверке»/«Готово к публикации») — заранее собранные комбинации тех же фильтров, не отдельная система состояний.

**Просрочка и «Требует внимания» — derived, не поле БД.** `getSmmContentAttentionReasons`/`isSmmContentOperationallyOverdue` (`smm-model.ts`) — ОДИН источник причин для обоих: просрочен дедлайн производства/монтажа (`OVERDUE_PRODUCTION`, при `IN_EDIT` берётся `MontageProject.deadlineDate`, не `ContentItem.deadline` — монтаж остаётся source of truth для своего срока), просрочена публикация (`OVERDUE_PUBLICATION`), нет монтажёра при `IN_EDIT` (`NO_EDITOR_IN_EDIT`), нет исходников при `WAITING_FOR_SHOOT`/`SHOT`/`IN_EDIT` (`NO_SOURCE_MATERIALS`), публикация `READY` без URL после плановой даты (`PUBLICATION_READY_NO_URL`). `PUBLISHED`/`CANCELLED` — всегда без причин. Шире, чем прежняя `isSmmContentOverdue` (та смотрит только на `ContentItem.deadline`, продолжает без изменений использоваться дашбордом хаба) — не вторая параллельная формула, а более полный derived-расчёт для операционного экрана.

**«Передать в монтаж»** — `linkSmmContentToMontage` (расширен в 2B) по-прежнему вызывает существующий `createMontageProject`, теперь дополнительно принимает `editorId`/`deadlineDate`/опциональные `workAmount`+`workType`. `SmmWorkItem` создаётся ТОЛЬКО если пользователь явно указал сумму работы при передаче — нет автосоздания оплачиваемой работы с ценой 0₽ «для порядка». Статус `ContentItem` автоматически переходит в `IN_EDIT` при передаче из `IDEA/PLANNED/WAITING_FOR_SHOOT/SHOT` (расширено в 2B — раньше срабатывало только для `IDEA/PLANNED`, что не покрывало реалистичный момент «уже отснято, отдаём в монтаж»).

**Публикации — quick-publish и метрики.** «Опубликовать» в карточке — одно действие (`updateSmmPublication` теперь принимает `Partial<SmmPublicationInput>` — реальный частичный апдейт, который уже существовал в реализации, просто был неверно типизирован как обязательный) сразу выставляет `status=PUBLISHED`+`url`+`publishedAt` (по умолчанию «сейчас», редактируемо), не требуя трёх отдельных правок. Добавление метрики создаёт НОВЫЙ снимок `SmmPublicationMetric`, никогда не перезаписывает старый (см. «Метрики публикации» выше — тот же принцип, просто теперь доступно прямо из Production).

**Родитель/дети** — «Создать производный контент» из карточки создаёт новый `SmmContentItem` с `parentContentId`, БЕЗ автокопирования названия/ТЗ (пользователь заполняет сам) — использует тот же `createSmmContentItem` и ту же защиту от циклов (`wouldCreateContentParentCycle`), что и раньше.

**Content Code — composite unique в пределах проекта (новое в 2B).** `@@unique([smmProjectId, contentCode])` добавлен в схему ПОСЛЕ проверки прод-данных (0 строк `SmmContentItem` на момент добавления — проверено read-only скриптом, см. `DATA_SAFETY.md`) — коллизий не было и не могло быть. Уникальность — В ПРЕДЕЛАХ проекта, не глобально (у разных клиентов легитимно бывают одинаковые коды); Postgres не считает несколько NULL конфликтующими в составном unique-индексе, поэтому единицы контента без кода по-прежнему создаются свободно. `createSmmContentItem`/`updateSmmContentItem` превращают Prisma `P2002` в понятную ошибку «Такой Content Code уже используется в этом проекте», а не общий текст.
