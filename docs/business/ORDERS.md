# ORDERS.md — заказы и расписание

## [CURRENT] Концептуальное разделение

`Order` — CRM/рабочая сущность. `ScheduleEvent` — аннотация расписания и детали бронирования. Одна коммерческая съёмка может использовать обе сущности одновременно (связанный заказ) или только `Order` (незапланированная работа, например чистый монтаж) или только `ScheduleEvent` (запись в расписании без заказа).

Google Calendar — внешний источник времени/заголовка/описания события. Платформа хранит аннотации и рабочее состояние поверх него; изменения обратно в Google Calendar не пишутся (см. `docs/integrations/GOOGLE_CALENDAR.md`).

## [CURRENT] Карточка заказа — какой компонент канонический (2026-08-02, исправлено)

**[RULE] Карточка коммерческого заказа, открываемая с дашборда, является каноническим UI. Все точки входа переиспользуют её. Отличия допустимы только в адаптерах загрузки, закрытия и обновления родительского экрана.** Компонент — `EventCardModal.tsx` (`src/app/(admin)/admin/schedule/EventCardModal.tsx`). Название файла — историческое (компонент много лет был картой конкретного события расписания до того, как стал общей канонической карточкой заказа); ориентироваться на факт (единственный UI-компонент, экспортируемый оттуда), а не на имя файла.

Ранее (короткий период 2026-08-02, коммит «Этап 2») это правило было сформулировано наоборот — канонической была объявлена `OrderFormModal.tsx`, а `EventCardModal.tsx` обрезана до некоммерческого режима. Это оказалось ошибкой: `EventCardModal.tsx` — многолетне отлаженный, визуально и функционально эталонный UI (комментарий/нюансы первым блоком, тип события, съёмка, гримёр, клиент, оплата, монтаж, материалы, документы, единая тёмная стилистика), а `OrderFormModal.tsx` — вторичная форма, использовавшаяся только в CRM/«Заказы» и никогда не достигавшая того же визуального стандарта. Решение отменено в этом же коммите: `EventCardModal.tsx` восстановлена целиком (включая некоммерческие записи — она обслуживает оба случая через условные секции по `requiresFullBookingForm(eventType)`, как и до Этапа 2), и в неё добавлен только один новый элемент — компактный селектор «Статус» (воронка `Order`) в шапке под датой/временем, видимый только когда у записи уже есть заказ (`annotation.orderId`).

**[CURRENT] Точки входа на `EventCardModal.tsx`:** Дашборд (`BookingIssuesBlock.tsx`), Расписание (`ScheduleView.tsx`), «Клиенты» → непривязанные записи (`PendingScheduleClients.tsx`), история съёмок в карточке клиента (`ClientTabs.tsx`), Финансы → Абонементы (`SubscriptionDetailModal.tsx`), CRM-доска (`OrdersBoard.tsx`), архив CRM (`OrdersArchiveView.tsx`), таблица «Заказы» (`OrdersListView.tsx`) — для любой уже существующей записи (некоммерческое событие, или коммерческое с привязанным `Order`).

**[RULE] Адаптер `Order` → каноническая карточка — `buildVmFromOrder()` (`src/lib/actions/orders.ts`).** Точки входа, у которых на руках только `OrderDTO` без живого события Google Calendar (CRM-доска/архив, «Заказы» — они никогда не имели дела с календарём напрямую), строят `ScheduleEventVM` через эту функцию: подгружает связанный `ScheduleEvent` по `order.scheduleEventId`, собирает `calendarEvent`-совместимый снэпшот из его полей (`title`/`startAt`/`endAt`) вместо живых данных календаря, и помечает VM полем `orderOnly: { orderId }`, если у записи нет `calendarEventId` (бронь никогда не синхронизировалась с календарём — например создана прямо в CRM). Точки входа, у которых уже есть живой `calendarEvent` (Дашборд, Расписание, карточка клиента, Абонементы), в адаптере не нуждаются — `ScheduleEventVM` у них уже собран через `mergeScheduleEvent`.

**[RULE] Сохранение через `updateOrder`, а не `upsertScheduleEvent`, когда `vm.orderOnly` заполнен.** `upsertScheduleEvent` — upsert строго по `calendarEventId`, которого у таких записей нет и не появится (Google Calendar — read-only, см. `GOOGLE_CALENDAR.md`). `EventCardModal.tsx` определяет это через единую точку `saveCore()`, которую используют и явное «Сохранить», и автосохранение — не два разных места, решающих, каким действием сохранять. `OrderInput` (`actions/orders.ts`) расширен полем `camerasCount` специально для этого адаптера — раньше писалось только через `upsertScheduleEvent`.

**[TARGET] Заявка без брони (`Order.scheduleEventId === null`) — вне рамок текущего адаптера.** `buildVmFromOrder()` возвращает `data: null` для таких заказов; вызывающая точка входа временно открывает старую `OrderFormModal.tsx` (`../crm/OrderFormModal`) как единственный оставшийся сценарий её использования, наравне с формой создания нового заказа с нуля («Создать заказ» в CRM/«Заказы», `order={null}`, и создание заказа из Telegram-диалога в `ConversationView.tsx` — эти два сценария в принципе не открывают существующую запись, поэтому не входят в унификацию). Отдельная будущая задача: адаптер для «заявки без брони» (сборка синтетического `calendarEvent` без всякого `ScheduleEvent` в основе) и последующее полное удаление `OrderFormModal.tsx`, когда её не останется использовать вовсе.

**[RULE] Переклассификация некоммерческой записи в коммерческую внутри `EventCardModal.tsx`.** Если администратор меняет `eventType` на коммерческий (`requiresFullBookingForm` становится `true`) и нажимает «Сохранить» — сохранение проходит как обычно (создаётся `Order` через `ensureOrderForNewBooking`), карточка не закрывается и не переоткрывается — она и так каноническая, дополнительных действий не требуется (в отличие от временной схемы Этапа 2, где это был переход в другой компонент).

## [RULE] Каноничный приоритет для связанных записей

Для заказа, связанного с событием расписания: поля `ScheduleEvent` имеют приоритет над пересекающимися полями `Order` при чтении. Это применяется как минимум к комментариям/заметкам, типу акции (promotion), цене/оплате, залу/времени, материалам и другим данным бронирования, отображаемым через DTO заказа (`toDTO()` в `src/lib/actions/orders.ts`).

**[CURRENT] (2026-08-02)**: тот же дуал-сорсинг распространён на `eventType` и поля выезда — `OrderDTO.eventType`/`shootAddress`/`venueName`/`venueContact`/`logisticsComment` читаются из `row.scheduleEvent`, `null` у заявок без записи; `OrderDTO.scheduleEventId` — id связанной записи, добавлен, чтобы карточке заказа было по чему находить сущности, ключующиеся по `scheduleEventId`, а не по `orderId` (см. `SubscriptionUsage.scheduleEventId` в схеме). `OrderDTO.subscriptionUsage` расширен до полной формы `ScheduleEventSubscriptionInfo` (`subscriptionId`/`usedHours`/`purchasedAt`/`packageHours`/`remainingHours`) — раньше это был усечённый ad-hoc тип только для чтения; используется временной `OrderFormModal.tsx` для заявок без брони (см. выше) — та же `SubscriptionPaymentBlock.tsx`, что и в канонической `EventCardModal.tsx`, не вторая независимая реализация.

**[CURRENT]** Оплата абонементом в канонической карточке доступна только когда у заказа уже определена дата/время И привязан клиент (`clientId`). Известный edge case: у отдельных исторических записей `ScheduleEvent.subscriptionUsage` уже заполнен (списание есть), а сам `Order.clientId` — нет (заказ никогда не был привязан к клиенту, притом что списание идёт с абонемента другого клиента, например когда бронирование оформлено на имя присутствующего человека, а платит владелец абонемента). Для таких заказов блок оплаты абонементом в карточке недоступен для редактирования, пока клиент не привязан — заслуживает отдельной задачи, если понадобится массово чистить такие записи.

**[RULE]** Не создавать вторую систему синхронизации. При расширении пересекающихся полей: (1) решить, какая модель канонична; (2) обновить общий merge DTO в `src/lib/actions/orders.ts`; (3) обновить всех писателей согласованно; (4) протестировать связанные и несвязанные заказы отдельно.

## [CURRENT] Комментарии

- `ScheduleEvent.description` — технический снимок описания из Google Calendar.
- `ScheduleEvent.notes` — единственное редактируемое поле «Комментарий / нюансы» для бронирования.
- Только при первой аннотации/сохранении описание календаря может засеять `notes`.
- Последующая синхронизация календаря НЕ должна перезаписывать отредактированные администратором `notes`.
- `Order.comment` обслуживает заказы без связанного события расписания и участвует в том же установленном merge-поведении при чтении.
- `Order.financeComment` — отдельная внутренняя финансовая информация, никогда не показывается как комментарий бронирования (см. `FINANCE.md`).

## [RULE] Типы события (`EventType`) — новый тип интегрируется, не копируется

Перенесено из `AGENTS.md` (был добавлен 2026-07-27 вместе с `OFFSITE_SHOOT`, вторым коммерческим типом события рядом со `STUDIO_BOOKING`). Правила ниже — прямое следствие этой задачи, не абстрактная теория.

1. **`ScheduleEvent.eventType` и `ScheduleEvent.format`** (`FORMAT_DICTIONARY` в `src/lib/import/normalize.ts`) — два независимых справочника. Текстовое совпадение значений («Выездная съёмка» есть в обоих) — не конфликт и не повод объединять поля.
2. **Выездная съёмка не привязана к студийному залу.** `ScheduleEvent.room`/`Order.room` остаются nullable для всех типов; фиктивный зал вроде `"Выезд"` не заводится, зал не требуется на уровне валидации для `OFFSITE_SHOOT`. В `EventCardModal.tsx` (канонической карточке) поле «Зал» показывается только при `eventType === 'STUDIO_BOOKING'`, иначе — статичная подпись «Локация: выездная»; адрес живёт в `shootAddress`/`venueName`/`venueContact`/`logisticsComment`.
3. **Часы выездной съёмки не входят в KPI «Часов в студии».** `isStudioBooking` (`src/lib/event-category.ts`) читается напрямую `DashboardBody.tsx` и `HoursReportBody.tsx` по сырому заголовку календаря (не по сохранённому `eventType`) и явно возвращает `false` для заголовков с «выезд» (`isOffsiteShootTitle`). **[RULE]** Правка для третьего «нестудийного» типа события идёт сюда же, не в дашборд/отчёт напрямую.
4. **Новый тип события интегрируется через `requiresFullBookingForm(eventType)`** (`src/lib/event-type.ts`), не через россыпь `eventType === 'STUDIO_BOOKING'` по компонентам. Этот хелпер — единственное место, решающее полноту формы заказа и участие в `canCheckBookingIssues` (`schedule-model.ts`) и фильтрах по клиенту (`client-shoots.ts`, `getClientScheduleBookings`). Точечные проверки конкретного значения enum вне `event-type.ts` — регрессия.
5. **Список опций «Тип события» — только `EVENT_TYPE_LABELS`** (`event-type.ts`). Порядок объекта = порядок пунктов `<select>` (`Object.keys(EVENT_TYPE_LABELS)`). Второй список типов события в отдельном компоненте не заводится.
6. **Условные поля карточки события зависят только от `eventType`**, не от отдельного локального стейта. Блок «Выезд» в `EventCardModal.tsx` рендерится по `eventType === 'OFFSITE_SHOOT'` напрямую.
7. **Массовая реклассификация исторических записей не выполняется без dry run и подтверждения владельца.** `classifyEventType` — живой fallback ТОЛЬКО для событий без сохранённой аннотации; сохранённый `ScheduleEvent.eventType` никогда не перезаписывается автоматически при доработке классификатора.

**[CURRENT] Прецедент 2026-07-27**: до фикса события с заголовком «выезд» уже задваивались в KPI часов студии как `STUDIO_BOOKING`/`OTHER` — сам факт был обнаружен и исправлен вместе с добавлением `OFFSITE_SHOOT`, не отдельной задачей.

## [RULE] Представление оплаты

`getOrderPaymentSummary()` (`src/lib/payment-model.ts`) — единственная функция для отображения оплаты на уровне заказа. Нормализует связанные данные расписания, статус заказа, способ оплаты, использование абонемента. **[RULE]** Статус оплаты не выводится независимо в таблицах/карточках заново.

## [CURRENT] Акции

Скидка первого визита — структурированные данные (`OrderPromotionType.FIRST_VISIT_20`), не текст внутри комментария. `promotion-model.ts`. Детекция/очистка легаси-текста — поведение совместимости, не предпочитаемый путь записи.

## [CURRENT] Статус и архив

Рабочий статус заказа и архивный overlay — разные понятия:
- статус отражает бизнес-прогресс;
- `isArchived`/`archivedAt`/`archiveReason` — состояние видимости/хранения;
- завершённый/отменённый статус не заменяется на `ARCHIVED` только чтобы архивировать запись;
- отменённые и удалённые/черновые записи не участвуют в финансовых агрегатах заказов.
