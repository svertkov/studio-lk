# MONTAGE.md — монтаж

## [CURRENT] Владение и связи

Монтажный проект (`MontageProject`) может быть привязан к заказу или существовать самостоятельно. Для заказных проектов клиент читается через `order.clientId`; это отношение не дублируется в `MontageProject.clientId` (подтверждено построчной сверкой с кодом).

**[RULE]** Автоматическое создание проекта монтажа для заказа должно оставаться идемпотентным. Схема допускает несколько проектов на заказ для будущих продуктов, но текущее (v1) автоматическое поведение не должно создавать дубликаты.

**[RULE] Почему `MontageProject.orderId` НЕ `@unique` — сознательное решение, подтверждённое аудитом 2026-08-04.** Второй проект монтажа на тот же заказ — не гипотетическая возможность «на будущее», а уже реализованная и используемая функция: `createMontageProject` принимает `confirmDuplicateForOrder` (ТЗ п.18) — форма отдельной карточки монтажа (`MontageProjectModal.tsx`) явно предупреждает администратора и предлагает подтвердить создание ещё одного проекта для заказа, у которого уже есть проект (реальный сценарий: повторный монтаж/доп. ролик как отдельная платная работа). Жёсткий `@unique` на `orderId` сломал бы эту функцию. Аудит 2026-08-04 подтвердил на реальных данных: 0 заказов с более чем одним проектом монтажа сейчас, 76 из 80 проектов — исторический импорт (`importSource='google_sheets_montage'`, `orderId=null`, ожидаемо), 0 «осиротевших» записей (`orderId=null AND importSource=null`); поля `scheduleEventId` у `MontageProject` не существует вовсе — привязка «только через запись расписания, без заказа» структурно невозможна.

- **Как встроенный редактор (`EmbeddedMontageSection.tsx`) выбирает проект при нескольких активных.** `getMontageProjectsForOrder` возвращает проекты заказа отсортированными `createdAt: 'desc'`; `activeProject = projects.find(p => p.status !== 'CANCELLED')` детерминированно берёт САМЫЙ НЕДАВНО СОЗДАННЫЙ активный — не случайный/неоднозначный выбор, а осознанное правило «последний созданный — текущий рабочий». **[TARGET]** Если у заказа реально два одновременно активных проекта монтажа, из карточки заказа доступен только этот один — более старый(-е) виден(ы) только через раздел «Монтаж» (`/admin/editing`). Это принятое ограничение, не баг — встраивание в карточку заказа рассчитано на типовой случай «один проект на заказ», редкий случай нескольких активных проектов обслуживается отдельной карточкой монтажа, как и раньше.
- **Почему `find`+`update` не создают неоднозначность при коммите формы.** `EmbeddedMontageSection.commitMontage()` обновляет РОВНО ТОТ проект, что уже показан администратору в открытой форме (тот же `activeProject`, полученный тем же самым детерминированным правилом выше) — не выбирает заново вслепую. Двойной клик/повтор не может создать дубликат, потому что коммит никогда не создаёт — только `getMontageProjectsForOrder` (чтение) → `updateMontageProject` (обновление найденного).
- **Гонка АВТОМАТИЧЕСКОГО создания — реальная, найдена и исправлена (не за счёт unique constraint).** До исправления `ensureMontageProjectForOrder` держала идемпотентность на паре `count()` → `create()` без общей транзакции — классический TOCTOU: два вызова для одного `orderId`, стартовавшие почти одновременно (например, автосохранение карточки заказа сработало на долю секунды раньше явного «Сохранить»), оба могли увидеть `count()===0` до того, как первый закоммитил `create()`, и создать по проекту каждый. Исправлено Postgres advisory-lock’ом (`pg_advisory_xact_lock(hashtext(orderId))`) внутри `prisma.$transaction` — сериализует конкурентные вызовы именно АВТОсоздающего пути сам с собой по конкретному `orderId`, не трогая ручной путь `createMontageProject`/`confirmDuplicateForOrder`. Проверено конкурентным скриптом `scripts/montage-concurrency-check/check.ts` (два и более по-настоящему параллельных `Promise.all`-вызова на один `orderId` → ровно один проект, во всех прогонах).
- **[RULE] Процесс «сохранить заказ → создать/обновить проект монтажа» — идемпотентный и восстанавливаемый, НЕ атомарный в смысле единой БД-транзакции.** Сохранение заказа/записи расписания и запись значений формы монтажа (`commitMontage`) — два последовательных серверных действия, второе неизбежно зависит от ответа первого клиенту (значения встроенной формы физически не могут уйти на сервер раньше, чем клиент узнает `orderId` только что созданного заказа) — построить это как одну общую транзакцию невозможно в принципе, не только нежелательно. Устойчивость к частичному сбою обеспечивается не атомарностью, а тем, что каждый шаг идемпотентен и умеет самовосстановиться при повторе:
  - если создание заказа/записи расписания упало — ничего не сохранилось, обычный повторный сценарий;
  - если заказ/запись сохранились, но конкретно создание проекта монтажа (`ensureMontageProjectForOrder`) упало (сеть, БД) — заказ остаётся с `editingRequired=true` и БЕЗ проекта; при следующем открытии карточки `EmbeddedMontageSection.commitMontage()` САМА обнаруживает отсутствие проекта и повторно вызывает ту же идемпотентную `ensureMontageProjectForOrder` перед тем, как показать ошибку — пользователю не нужно вручную ничего чинить, повторное «Сохранить» само восстанавливает состояние (проверено живьём: искусственно созданный заказ с `editingRequired=true` без проекта монтажа → открытие карточки → «Сохранить» → проект создаётся, ошибки нет). Автоматический авто-переход статуса заказа при сохранении (`upsertScheduleEvent`/`updateOrder`) срабатывает только на переходе `false/null → true`, а не «уже true, но проекта нет» — это осознанно оставлено только там (не про существование проекта монтажа, отдельная задача воронки), самовосстановление именно для проекта монтажа живёт в `commitMontage`;
  - если проект монтажа создан, но `commitMontage` (запись значений формы) упала — проект уже существует с серверными значениями по умолчанию; повторное открытие карточки и «Сохранить» находит его через `getMontageProjectsForOrder` и обновляет, не создавая второй.

## [RULE] Встраивание в карточку заказа (2026-08-03)

До этой доработки выбор «Монтаж требуется» в карточке заказа показывал только заглушку («появится после сохранения») — администратор был вынужден сначала сохранить заказ, затем отдельно найти и открыть карточку монтажа, что приводило к незаполненным/забытым проектам в CRM. Теперь выбор сразу разворачивает полный редактор с тем же набором полей, что и отдельная карточка монтажа.

- **Источник истины и переиспользование.** Единственная сущность — `MontageProject`; единственный редактор полей — `MontageProjectFields.tsx` (`src/components/montage/`), извлечённый из бывшей монолитной `MontageProjectModal.tsx` (`admin/editing/`, теперь тонкая обёртка вокруг него для сценария создания-с-нуля/привязки к заказу). Он используется БЕЗ ИЗМЕНЕНИЙ в двух местах: отдельная карточка монтажа и `EmbeddedMontageSection.tsx` — обёртка, встроенная в `EventCardModal.tsx`/`OrderFormModal.tsx` (см. `ORDERS.md`). Общие тип формы, mapping API↔форма и валидация — `src/lib/montage-model.ts` (`MontageProjectFormValues`, `buildMontageFormValues`, `montageFormValuesToInput`, `isMontageFormEmpty`, `diffMontageFormValues`) — нет второй, упрощённой формы для встроенного случая.
- **Создание — только через `ensureMontageProjectForOrder`.** `EmbeddedMontageSection` никогда не вызывает `createMontageProject` напрямую — только читает (`getMontageProjectsForOrder`) и обновляет найденное (`updateMontageProject`); если после сохранения заказа проекта всё ещё нет (частичный сбой предыдущего шага), сама повторно и безопасно вызывает `ensureMontageProjectForOrder` перед тем, как сдаться. Про конкурентную защиту самого автосоздания, про то, почему нет `@unique` на `orderId`, и про идемпотентность/восстанавливаемость всего процесса целиком — см. «Владение и связи» выше (аудит 2026-08-04).
- **[RULE] `diffMontageFormValues`, а не полный `montageFormValuesToInput`, для встроенного коммита.** Форма встроенного редактора может смонтироваться с `project=null` (заказ ещё не сохранён), а реальный проект — появиться на сервере уже ПОСЛЕ монтирования (например через автосохранение карточки заказа, которое сработало раньше явного «Сохранить»). Полный набор значений в этом случае затёр бы серверные значения по умолчанию (дата поступления в монтаж, автоугаданное название) пустыми полями, которые администратор не трогал — реальный баг, найденный при живом тестировании 2026-08-03. `diffMontageFormValues` (`montage-model.ts`) сравнивает текущие значения формы с тем, с чем она была смонтирована, и отправляет только реально изменённые поля — непотронутые уходят как `undefined`, `updateMontageProject` (тот же дуал-сорсинг, что у `Order`/`ScheduleEvent`) оставляет для них то, что реально лежит в БД. Отдельная карточка монтажа продолжает использовать полный `montageFormValuesToInput` — там формы гонки нет, editing всегда начинается с уже загруженного реального проекта.
- **Отключение «Монтаж требуется».** Два разных случая, разные диалоги: (1) черновик ещё не сохранён (`MontageDraftDiscardDialog.tsx`) — предупреждает о потере введённых данных, ничего не создаёт на сервере при подтверждении (проект физически никогда не существовал); (2) проект уже существует (`MontageDisableChoiceDialog.tsx`, не изменён этой доработкой) — предлагает оставить/приостановить/отменить/архивировать, никогда не удаляет проект молча.
- **Отображение.** `revalidateMontagePaths` (существовавшая функция, не изменена) уже инвалидирует «Монтаж», CRM, «Заказы», карточку клиента, финансы и дашборд при любой мутации проекта — встроенный редактор не требует отдельной инвалидации, использует те же серверные действия (`updateMontageProject`), что и отдельная карточка.

## [CURRENT] Статусы (2026-07-08, упрощение до 5 статусов)

Производственный статус, пауза, отмена и архив — разные концепции, каждая со своей семантикой:
- **пауза** (`isPaused`) — overlay, обратима;
- **отмена** (`cancelledAt`) — терминальна;
- **архив** (`isArchived`) — overlay поверх статуса, не заменяет его.

Пауза/отмена/архив вынесены в оверлейные действия поверх карточки (2026-07-08: до этой правки было 14 значений статуса производства, сокращено до 5, а пауза/отмена/архив выделены в отдельные оверлеи) — не смешиваются с самим статусом производства.

## [RULE] Финансы

Сумма клиента и сумма редактора монтажа — независимые поля. Прибыль вычисляется из этих полей через `montage-model.ts`; не копируется в выручку заказа, прибыль заказа или исторические визиты. **[RULE]** «Прибыль по заказу» (см. `FINANCE.md`) и P&L монтажа — разные понятия, не путать. `computeCombinedFinanceSummary` (`finance-model.ts`) объединяет их для страницы «Финансы», не пересчитывая заново в `page.tsx` (см. `FINANCE.md`, «Текущая осторожность»).
