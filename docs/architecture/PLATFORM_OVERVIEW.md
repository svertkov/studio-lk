## [CURRENT] Стек и рантайм

- Next.js 16 (App Router), React 19, TypeScript 5.
- Tailwind CSS 4 + shadcn/ui на `@base-ui/react`.
- Prisma 5 + PostgreSQL (Yandex Cloud Managed, единая база для dev и prod).
- Auth.js / NextAuth v5, credentials-провайдер.
- Vitest — только для чистых доменных функций (`vitest.config.ts` явно ограничивает область `src/**/*.test.ts`, `scripts/**/*.test.ts`, node-окружение); нет установленной практики интеграционных/UI-тестов «из-за отсутствия тестовой БД» (комментарий в самом конфиге).
- Деплой — Vercel, без автоматического деплоя при push в основную ветку — после каждого push для попадания изменений на прод требуется вручную выполнить `vercel --prod`.
- Внешние интеграции: Google Calendar (read-only), Telegram Bot API, Google Sheets (историческая миграция), Anthropic API (`src/lib/import/ai-classify.ts` — AI-классификация исторического импорта, реальная интеграция, не описанная ни в одном документе исходного пакета), Vercel Blob (только как транзитный релей для исходящих Telegram-вложений, см. `docs/integrations/TELEGRAM.md`).
- **[RULE]** Next.js в этой версии может отличаться от общеизвестных конвенций — перед использованием API читать `node_modules/next/dist/docs/`, не полагаться на память о более старых версиях.

## [CURRENT] Ключевые связи сущностей

- `Client` — канонический владелец персональных/контактных/юридических данных.
- `ScheduleEvent` — аннотация события Google Calendar либо запись, созданная вручную; независимый справочник `eventType` (см. `ORDERS.md`).
- `Order` — CRM/рабочая запись; может быть связана с `ScheduleEvent`, `Client`, Telegram-диалогом, документами, `ClientVisit`, монтажными проектами.
- `ClientVisit` — историческая импортированная посещаемость/выручка, НЕ взаимозаменяема с `Order`.
- `ClientSubscription` + `SubscriptionUsage` + `SubscriptionAdjustment` — учёт часов абонемента (детали — `SUBSCRIPTIONS.md`).
- `MontageProject` — принадлежит заказу либо существует самостоятельно; для заказных клиент читается через `order.clientId`, не дублируется.
- `Document` — структурированный реестр (номера/статусы), НЕ файловое хранилище.
- `Expense` — отдельный реестр обязательств/расходов.

## [CURRENT] Единственный список известных архитектурных рисков

**Другие документы этого комплекта ссылаются на эти пункты по номеру («см. риск №N»), не копируют формулировки.**

1. **Одна база данных на dev и prod.** Любая рутинная команда схемы/очистки способна изменить прод-данные. Доминирующий риск, всё остальное вторично. См. `DATA_SAFETY.md`.
2. **Нет версионированной истории миграций Prisma.** `prisma db push` быстр, но слаб для ревью/отката/воспроизводимости.
3. **Нет CI-проверки типов/линта/тестов/сборки.** Ни один коммит не проходит автоматическую проверку перед попаданием в основную ветку.
4. **Несколько центральных компонентов и action-файлов превышают 700–1500+ строк** (список — раздел «Слои» выше). Риск связности и регрессий при правках.
5. **Гранулярный RBAC не реализован.** Единственное жёсткое разграничение сейчас — роль `CLIENT` не допускается в админ-раздел; внутри админки (`OWNER`/`ADMIN`/`OPERATOR`/`EDITOR`) разграничения нет почти нигде. См. `SECURITY.md`.
6. **В схеме остаются устаревшие поля обратной совместимости** после изменения бизнес-правил (пример: `Order.netProfitMode` и старые override-поля прибыли — правило теперь полностью ручное, поля исторические).
7. **Финансовые данные объединяют несколько исторических и текущих источников** (текущие заказы, `ClientVisit`, монтаж, расходы) — любое изменение требует явного решения об объёме (scope), иначе риск двойного счёта или конкурирующих определений «прибыли». См. `FINANCE.md`.
8. **`supabase/` — вероятно исторический артефакт**, не подтверждённый как часть текущей архитектуры.

**[RULE]** Не выполнять оппортунистические широкие рефакторинги внутри задачи по фиче. Выносить только те швы, которые необходимы для корректности текущей задачи; более крупные рефакторинги — предлагать отдельно, не смешивать с текущей задачей.
