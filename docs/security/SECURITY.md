# SECURITY.md — модель доступа API-маршрутов

**[RULE]** Правило платформы: ни один API-маршрут не может существовать без явно выбранной модели доступа. «Забыли добавить проверку» — не нейтральное состояние, а дыра. Отсутствие защиты допустимо только как осознанно подтверждённое владельцем решение для конкретного маршрута (публичный маршрут), а не как значение по умолчанию.

## Модели доступа (единственные разрешённые варианты)

1. **Сессия сотрудника** (`auth()` из `@/auth` + проверка `session.user.role`). Стандарт для всех маршрутов, обслуживающих админ-интерфейс.
2. **Проверка роли поверх сессии** — сессия + сужение по конкретным ролям (например только `OWNER`), когда доступ уже к самой сессии недостаточен.
3. **Секрет в заголовке `Authorization`** (переменная окружения `CRON_SECRET`) — для маршрутов, вызываемых планировщиком (Vercel Cron/внешний), без пользовательской сессии.
4. **Секрет вебхука в заголовке** (`X-Telegram-Bot-Api-Secret-Token`, переменная `TELEGRAM_WEBHOOK_SECRET`) — для входящих вебхуков от внешнего сервиса.
5. **Явно подтверждённый владельцем публичный маршрут** — единственный вариант без проверки; требует отдельной пометки в этом документе с датой и обоснованием. **[CURRENT]**: таких маршрутов в проекте сейчас нет.

## [RULE] Чек-лист для нового API-маршрута

1. Определить: обслуживает ли маршрут админ-интерфейс, внешний планировщик, входящий вебхук или что-то ещё — выбрать соответствующую модель из списка выше.
2. Если маршрут обслуживает админ-интерфейс — модель доступа должна повторять `(admin)/layout.tsx`: `if (!session) redirect('/staff-login'); if (session.user.role === 'CLIENT') redirect('/dashboard')`. Не сужать до конкретных ролей (например только `OWNER`/`ADMIN`) без явной причины — иначе есть риск случайно заблокировать `OPERATOR`/`EDITOR`, которым сам админ-раздел уже разрешён (см. прецедент ниже).
3. Сверить с СОСЕДНИМИ маршрутами того же типа (пример: новый cron-маршрут — сверить с `sync-expenses`/`sync-revenue`, а не изобретать новую схему секрета).
4. Не изобретать новый механизм авторизации — переиспользовать `auth()`, `CRON_SECRET`, паттерн вебхук-секрета из таблицы выше.
5. Проверить формат ответа при отказе в доступе: единый статус `401` и форма `{ error: string }` для «нет сессии» и «не та роль» — не два разных статуса на два похожих случая (см. `route.test.ts` в `api/calendar/events`, где это явно протестировано).
6. Добавить строку в таблицу инвентаризации выше в этом же PR/коммите.

## [CURRENT] Известные ограничения RBAC

- **[CURRENT]** Полноценного RBAC (управляемых разрешений по ролям) в проекте нет почти нигде — большинство проверок сводится к бинарному «есть сессия и роль не `CLIENT`» на уровне `(admin)/layout.tsx`, без более тонкого разграничения внутри админки между `OWNER`/`ADMIN`/`OPERATOR`/`EDITOR`.
- **[CURRENT]** Роль `Role` enum: `OWNER, ADMIN, OPERATOR, EDITOR, CLIENT`. Единственное жёсткое разграничение сейчас — `CLIENT` не допускается в админ-раздел вообще.
- **[TARGET]** Не предполагается автоматически, что более тонкий RBAC появится — это осознанно отложенное решение на масштабе «один владелец», а не забытая задача (см. также `docs/business/DOCUMENTS.md`, п. про отсутствие RBAC для документов).
- **[CURRENT]** DB-роль приложения (`studio_lk_user`) — владелец всех таблиц, нет отдельной урезанной роли для рантайма (см. `docs/development/DATA_SAFETY.md`).

## [RULE] Прецедент: `/api/calendar/events` без авторизации (до коммита `238ec35`)

До 2026-07-28 маршрут `GET /api/calendar/events` не проверял сессию вообще — любой, кто знал URL, мог получить содержимое рабочего Google-календаря студии, включая заголовки и описания событий, где по сложившейся практике записаны имена клиентов, телефоны и суммы (см. `parseEventTitle`). Обнаружено в ходе внешнего архитектурного ревью документации, не через инцидент в проде.

**Исправление**: добавлена проверка `auth()` перед основной логикой, с той же моделью, что уже применяется в `api/telegram/file/[attachmentId]/route.ts` — единый статус `401` и форма ответа для «нет сессии» и «не та роль», не новый механизм. Роль, которой запрещён доступ — только `CLIENT` (единственная роль, которой не разрешён админ-раздел вообще, см. `(admin)/layout.tsx`), а не более узкий список вроде `OWNER`/`ADMIN`, который бы по ошибке заблокировал `OPERATOR`/`EDITOR`.

**Практический вывод**: при любом ревью новой или существующей документации явно проверять, не описывает ли она маршрут как «защищённый» или «read-only» без верификации по коду — расхождение между тем, что документ ПРЕДПОЛАГАЕТ, и тем, что код РЕАЛЬНО проверяет, обнаруживается только чтением `route.ts`, не по названию маршрута или комментарию к нему.

**Коммит**: `238ec35`. **Тест**: `src/app/api/calendar/events/route.test.ts` (7 сценариев: без сессии → 401, роль `CLIENT` → 401, четыре разрешённые роли → 200 с прежним форматом ответа, ошибка Google Calendar при валидной сессии → 500 как раньше).
