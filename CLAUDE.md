# CLAUDE.md (проект) — индекс инженерной памяти платформы 2470

## 0. Порядок приоритета инструкций

**Уровень 0** — прямое указание владельца в текущем диалоге. Всегда выше любого файла.

**Уровень 1 — три файла с ОДИНАКОВЫМ, высшим после владельца приоритетом**: `AGENTS.md` (корень репозитория), `docs/security/SECURITY.md`, `docs/development/DATA_SAFETY.md`. Это не три независимых по значимости источника, а один уровень обязательных правил, разделённый на три файла только физически (ради читаемости и объёма), не по важности — ни один из них не «главнее» двух других. Все три всегда загружены. **Если формулировки этих трёх файлов кажутся противоречащими друг другу** — это ошибка в самих документах (несогласованность), а не повод молча выбрать один файл над другим: остановиться и сообщить владельцу, зафиксировав расхождение в `DOCS_DRIFT.md`, а не разрешать конфликт самостоятельным выбором приоритета.

**Уровень 2** — доменные документы в `docs/business/*`, `docs/integrations/*`, `docs/architecture/*`, `docs/development/UI_UX.md`. Читаются по требованию при работе в соответствующей области. Детализируют правила уровня 1, но не могут им противоречить или их переопределять.

**Уровень 3** — `DOCS_DRIFT.md`. Не источник правил, а список известных расхождений кода и документации; сверяться с ним перед тем, как считать любой документ уровня 1 или 2 на 100% актуальным.

## 1. Технически независимые принципы

Эти принципы не зависят от конкретного стека (Next.js/Prisma могут смениться — принципы нет) и применимы к любой задаче на этой платформе:

- **Единый источник данных.** Один и тот же заказ/клиент/оплата/абонемент виден одновременно из дашборда, CRM, «Заказов», расписания, карточки клиента, финансов и отчётов. Расхождение данных между экранами — баг архитектуры, а не косметика одной таблицы. Полный список из 10 обязательных правил и прецедент (тройное дублирование `FLOW_TYPES_REQUIRING_*`, 2026-07-19) — см. `AGENTS.md`, раздел «Единый источник данных и взаимосвязанность платформы».
- **Редактируемость связанных сущностей.** Любая отображаемая связанная сущность обязана иметь понятный путь редактирования, а не только создание/просмотр; редактор переиспользуется одним компонентом независимо от числа мест вызова. Полный список из 8 правил и прецедент (2026-07-22) — см. `AGENTS.md`, раздел «Редактируемость связанных сущностей».
- **Нет защиты по умолчанию недопустимо.** Любой новый API-маршрут обязан иметь явно выбранную модель доступа — не «забыли добавить проверку». Полная модель — см. `docs/security/SECURITY.md`.
- **Деструктивные операции против единственной прод-базы требуют дисциплины, а не героизма.** Один владелец, одна база (dev=prod), без CI/Docker — правила рассчитаны именно на этот масштаб, не на enterprise-паттерны. Полный список — см. `docs/development/DATA_SAFETY.md`.
- **Булевы бизнес-исключения никогда не реализуются как обычный checkbox без анализа бизнес-сценариев.** Прежде чем добавить новое булево поле — определить, это фильтр списка, безопасная настройка интерфейса, или значимое бизнес-исключение (тогда — только `ConfirmableStatusToggle`, с подтверждением и аудитом). Это правило обязано быть видно ДО открытия `docs/development/UI_UX.md`, а не только внутри него — именно потому, что плоский чекбокс является путём наименьшего сопротивления и легко проходит незамеченным вне UI-задач. Полное дерево решений и три категории — `docs/development/UI_UX.md`; связанный прецедент — `AGENTS.md`, раздел «Булевы бизнес-исключения».

## 2. Обязательный workflow для новой задачи

1. Проверить `AGENTS.md` (уже загружен) и, если задача трогает данные заказа/клиента/оплаты/абонемента — пройти чек-лист в его последнем разделе.
2. Если задача создаёт/меняет API-маршрут — свериться с `docs/security/SECURITY.md` и с соседними маршрутами того же типа (staff/cron/webhook), прежде чем решать модель доступа.
3. Если задача — ad-hoc скрипт, миграция или что-то, способное задеть прод-данные — свериться с `docs/development/DATA_SAFETY.md` до, а не после написания скрипта.
4. Если задача трогает область, описанную в `docs/business/*` или `docs/integrations/*` — открыть соответствующий файл перед началом работы, не полагаться на память о нём из предыдущей сессии.
5. Если в процессе работы обнаружено, что документ в `docs/` не соответствует коду — добавить запись в `DOCS_DRIFT.md` до завершения задачи, не откладывать «на потом».
6. Перед тем как считать задачу завершённой — свериться с чек-листом в конце `AGENTS.md` (источник истины / кто читает / кто пишет / инвалидация / дублирующие поля / тесты).
7. **Обязательный завершающий этап — запустить по порядку:**
   ```
   npx tsc --noEmit
   npm run lint
   npm run test
   npm run build
   ```
   Задача не считается завершённой, пока эти команды не выполнены. **Если какую-то из команд выполнить не удалось** (недоступна среда, конфликт версий, долгий таймаут и т.п.) — это обязательно указывается явно в итоговом отчёте по задаче (какая команда, почему не выполнена, что проверено вместо неё), а не замалчивается и не заменяется предположением «наверное, всё в порядке».

## 3. Безопасность — обязательные правила

- Ни один API-маршрут не может оставаться без явной модели доступа. Модели: сессия сотрудника (`auth()` + проверка роли), секрет в заголовке `Authorization` (cron), секрет в заголовке `X-Telegram-Bot-Api-Secret-Token` (webhook), или явно подтверждённый владельцем публичный маршрут (сейчас таких нет).
- Новый маршрут проверяется на соответствие модели доступа СОСЕДНИХ маршрутов того же типа и на соответствие `(admin)/layout.tsx`, если он обслуживает админ-интерфейс — не изобретать новую модель без причины.
- Прецедент: `/api/calendar/events` был без какой-либо проверки сессии до коммита `238ec35` (2026-07-27/28) — отдавал вживую содержимое Google Calendar (имена клиентов, телефоны, суммы в заголовках событий) кому угодно. Полная модель и разбор — `docs/security/SECURITY.md`.
